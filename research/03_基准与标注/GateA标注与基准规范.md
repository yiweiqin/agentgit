# Gate A：多会话 agent 代码变更失效基准与标注规范

> 场景锚点：本规范服务于**单开发者 × 多 agent 会话**这一主场景（见 `01_问题定义与定位/AI原生版本控制研究问题.md` §1.1）。
> “多 agent 自治协作”不在本规范的适用范围内，不得把两类场景的标注结果合并报告。

## 1. 目的与适用范围

本规范用于验证“AI 变更协调债务”（ACCD）的关键维度是否可以被独立标注者稳定识别。Gate A 只回答一个问题：

> 给定任务、并行变更、测试和集成上下文，软件工程经验丰富的标注者能否一致判断是否存在**可理解性侵蚀**、语义冲突、重复任务、概念冲突、无归属产物和集成债务？

本阶段不评价 ISCC 的检测准确率，也不评价在线治理是否改善开发效率。系统预测必须在标签冻结之后进行，以避免循环论证。

## 2. 样本单位

一个样本是一个 `scenario`，而不是一个文件或一个 diff。每个 scenario 包含：

```text
baseline_commit
task_pair_or_set
agent_context_summary
change_set_A / change_set_B / ...
individual_test_results
candidate_integration_result
post_integration_tests
repair_or_revert_history
```

最小样本应包含两个并行任务和两个变更集；若研究分支爆炸或生命周期问题，则增加 3–8 个并行 agent 的完整轨迹。样本必须说明变更顺序和合并顺序，因为相同变更在不同顺序下可能产生不同结果。

## 3. 标注者信息边界

为区分“系统可见证据”和“事后真值”，每个样本提供两种视图：

### 3.1 预测前视图

标注者可看到任务描述、验收条件、基线代码、并行变更、变更来源和变更前测试，但看不到系统预测结果。该视图用于判断：在集成之前，是否已经存在重复、潜在冲突或不完整归属。

### 3.2 结果视图

在完成预测前标注后，向标注者提供合并结果、测试差异、回滚/修复记录和后续提交。该视图用于确认实际的行为冲突、架构冲突、重复实现和集成债务。

两种视图的顺序不可交换。若标注者先看到合并失败，容易把“可预见风险”与“事后知道的事实”混淆。

## 4. 标签本体与判定顺序

每个标签有三个字段：`label`、`evidence`、`confidence`。`confidence` 取 `high`、`medium` 或 `low`；无法给出证据的判断不得标为 `high`。

### 4.1 文本冲突（TC）

**判定条件：** Git 三方合并产生冲突标记，或需要人工选择同一文本区间的不同版本。

**证据：** 合并命令输出、冲突文件列表、冲突标记或人工合并记录。

TC 是客观标签，不等于语义冲突。若只有 TC 而没有行为或架构后果，仍然不能标记 BC 或 AC。

### 4.2 行为冲突（BC）

**判定条件：** 合并后的代码违反至少一个在任务、测试、API 契约或输入输出不变量中明确声明的行为约束。

**必要证据之一：**

- 合并后原有测试失败，且失败原因可归因于两个并行变更的组合；
- 新增验收测试失败；
- API/schema/协议契约被破坏；
- 后续修复提交明确撤销或重写其中至少一个变更。

单纯“代码看起来不优雅”不能作为 BC 证据。

### 4.3 架构冲突（AC）

**判定条件：** 合并结果违反项目已有的模块边界、依赖方向、数据所有权或注册机制，即使当前测试尚未失败。

**必要证据之一：**

- 静态架构规则或 lint 规则失败；
- 维护者在审查或后续提交中明确指出违反架构约束；
- 依赖图出现被项目规范禁止的边；
- 同一资源的所有权或初始化责任出现两个互不兼容的实现。

只有“不同设计风格”而无项目级约束时，标注为 `uncertain`，不能直接标 AC。

### 4.4 重复任务（RT）

**判定条件：** 两个任务的验收条件在人工审查后具有实质重叠，完成其中一个任务会满足另一个任务的大部分核心验收条件。

**排除条件：** 仅仅都涉及同一个文件、都包含“增加测试”或使用相同领域词汇，不足以判定 RT。

建议记录 `overlap_ratio`：核心验收条件交集 / 两个任务核心验收条件并集。该比例是辅助证据，不是自动阈值。

### 4.5 重复实现（RI）

**判定条件：** 两个变更都实现了同一个能力，最终只保留一份，或其中一份被删除、回滚、重构为另一份的调用方。

RI 与 RT 可以独立出现：任务描述不同但实现目标重叠时可能只有 RI；任务重复但一个 agent 失败时可能只有 RT。

### 4.6 概念冲突（CC）

**判定条件：** 两个变更针对同一规范概念、业务状态或接口语义使用不一致的名称、类型、生命周期或约束，导致维护者无法把它们视为同一抽象。

**证据：** 领域模型、API 文档、schema、命名规范、测试断言或维护者裁决。仅有变量名不同不够；必须说明它们是否代表同一概念。

### 4.7 无归属产物（UA）

**判定条件：** 文件、代码片段、生成物或配置无法映射到有效任务、agent 和生命周期状态，且在场景结束时仍未被明确接受、废弃或解释。

UA 的“无法映射”必须在提供完整 agent 轨迹后判断，不能因为提交信息简短就直接标注。

### 4.8 集成债务（ID）

**判定条件：** 变更没有立即导致合并失败，但后续必须付出可观测返工、回滚、人工重构或额外验证成本，才能进入主线并满足任务目标。

ID 是结果性标签，至少需要记录成本证据：额外修改行数、额外人工时间、额外测试轮次、回滚次数或延迟。没有成本证据时只能标 `possible_ID`。

### 4.9 可理解性侵蚀（LF，Legibility failure）

**判定条件：** 同一代码实体被多个会话（或多次变更）反复触碰后，其**保留形态无法回溯到任何单一有效任务**。该条件成立即算，**不要求**行为被破坏、不要求文本冲突、不要求架构违规。

**必要证据之一：**

- 同一实体（函数、类、API、配置键）在观察窗口内被 3 个及以上不同变更触碰，且这些变更归属于不同任务；
- 后续提交虽然修改或重写了该实体，但其动机无法归属到任何已在案的任务；
- 该实体的当前形态包含无法由任一任务验收条件解释的部分（例如保留了两套并存且无一处被声明为废弃的路径）。

**不算：**

- 同一文件被多次修改，但每次都可清晰归属到不同任务且各自语义完整；
- 仅因为文件改动行数多、或提交次数多；
- 仅因为两个变更共享同一路径或同一符号（路径/符号重叠是筛选信号，不是本标签证据）；
- 仅因为提交信息简短。

**与冲突类标签的关系（必须写进论文）：** `LF` 与 `TC`/`BC`/`AC` **互斥于证据，不互斥于取值**——一个样本可以同时无冲突且有 `LF`。**不得因为 `TC = no` 或 `BC = no` 而判 `LF = no`**，那会将“未冲突”误读为“未被侵蚀”。反之，若一个样本同时有 `BC = yes` 与重复触碰证据，两者应分别标注，不得互相替代。

**本标签的地位：** 构念边界尚未经验证，属**探索性标签**，其一致性未达标时应降级或撤销，不得作为核心主张的证据（对应主文档 H6，若 H6 不成立则撤销本标签）。

## 5. 正例、负例和模糊例

每类标签至少收集三种样本：

- **正例**：证据充分，两个独立标注者应给出相同标签；
- **负例**：表面上有文件重叠或相似词汇，但不满足标签定义；
- **模糊例**：证据不完整或存在合理分歧，用于估计构念边界和改进手册。

论文必须同时报告三类样本，不能只发布容易判断的正例。模糊例不得静默删除；应报告其比例及最终裁决规则。

## 6. 标注流程

1. 标注者阅读预测前视图，独立填写所有标签、证据和置信度；
2. 系统锁定预测前标注，不允许回看修改；
3. 标注者阅读结果视图，补充结果性标签和成本证据；
4. 两名标注者进行一致性计算，不得先讨论；
5. 只对存在分歧的样本交给第三名裁决；
6. 记录原始标签、裁决标签、分歧原因和手册变更版本。

标注手册在试点阶段可以迭代，但每次修改必须冻结一个版本，并明确哪些旧样本需要重新标注。正式测试集标签生成后，手册不得针对模型输出再修改。

## 7. 一致性与质量门槛

对二元标签报告 Cohen's kappa；对多标签和置信度等级报告 Krippendorff's alpha 或 Gwet's AC1，并同时给出原始一致率。不能只报告一个整体分数，应分别报告 TC、BC、AC、RT、RI、CC、UA、ID。

进入 Gate B 前至少满足：

- 关键标签的置信度为 high 的样本有明确证据；
- **BC、RT、RI 三个核心标签**以及**探索性标签 `LF` 在降级前后的归属**的双人一致性达到预注册门槛；
- 分歧样本中，第三方裁决能解释分歧来源，而不是简单多数表决；
- 模糊例比例和标签缺失率被公开报告；
- 任一标签若一致性持续偏低，必须收缩定义或将其降级为探索性标签。

具体数值门槛应在试点前注册。若研究者希望使用常见经验阈值，应说明其适用范围，不能把任意阈值包装成普适标准。

## 8. 基准切分与泄漏控制

按项目和项目版本切分 train/dev/test，禁止同一项目相邻 commit 跨集合造成近重复泄漏。任务模板、agent 系统提示和自动生成的变更也应去重。

若使用历史真实 PR 作为样本，必须区分：

- 标注者当时可见的信息；
- 研究者利用后续历史重建出的结果真值。

检测器只能使用前者；后者只能用于离线标签和结果评估。

## 9. Gate A 交付物

Gate A 完成时应提交：

```text
benchmark/
  scenarios/             # 匿名化或可公开重放的样本
  labels_v1.jsonl        # 原始双人标签、裁决标签和证据引用
  annotation_manual.md   # 本规范的冻结版本
  adjudication_log.md    # 分歧、裁决和手册修改记录
  inter_rater_report.md  # 各标签的一致性和置信区间
  leakage_report.md      # 项目、任务和模板去重检查
  replay.sh / replay.ps1 # 从 baseline 重放场景的命令
```

没有这些交付物时，只能说“提出了标注计划”，不能说“ACCD 已被经验验证”。

## 10. Gate A 后允许提出的结论

若一致性和证据质量达标，可以谨慎地说：

> 在所覆盖的项目和任务分布内，语义冲突、重复工作和集成债务具有可操作的判定标准，可以作为后续检测和治理实验的测量对象。

不能据此直接说：

- ISCC 已经能准确检测这些问题；
- 多 agent 开发必然比人类协作更混乱；
- Git 在所有 AI 开发场景中都不再适用；
- 在线治理已经降低了开发成本。

## 11.1 真实历史候选队列的特殊约束

由提交图筛选器生成的 `annotation_queue.jsonl` 只能作为标注工作队列。它预填 PR 编号、merge SHA、时间重叠、共享路径和 patch 路径，但所有 ACCD 标签必须由两名独立标注者填写。筛选器或单个研究者的初审意见不得回填到 `labels_v1.jsonl` 作为正式真值。

候选 patch 下载后必须固定 SHA-256，并把下载失败、空文件和 HTML 错误页标为 `unusable_evidence`。标注者只能使用 manifest 中状态为 `downloaded` 且文件头为合法 patch 文本的证据；下载成功本身也不代表候选存在冲突。
