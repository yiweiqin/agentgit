# 痛点方案候选与顶会达标检验

## 0. 这份文档回答什么

把用户的原始观察（多个 agent 会话并行开发 → 同一处被反复改、重复实现、工作区脏、分支合不上）迭代成**多版**可投稿的问题定义，并对每一版做**逐维度的达标检验**：它在当前证据下能不能过顶会评审；如果不能，唯一缺口是什么、补什么、成本多大。

三条必须说清的使用限制：

1. **这不是录用保证。** 下面做的是**结构化达标审查**（reviewer-simulation）：把顶会评审的通用判据操作化成可判定的维度，再用仓库当前状态去逐项核验。它能把"明显过不了"的方案筛掉、把"只差一个具体缺口"的方案识别出来，但不能证明某版一定被接收。
2. **判定必须基于当前状态，不是基于计划。** 每一版的结论都引用 `03_基准与标注/` 下可复现的实测事实（见 §6）。
3. **版本之间不是互斥的。** 五版里有的是"钩子"（提供新颖性），有的是"容器"（承载机制与系统）；§7 给出组合策略，而不是让你只选一个。

## 1. 判定标准：把「顶会要求」操作化

不同会议的评审表措辞不同，但研究轨（ICSE / FSE / ASE / CSCW / CHI / EMSE）实际反复考察的是同一批东西。把它们拆成 10 个可判定维度：

| 维度 | 通过判据（必须可验证） | 证据形式 |
|---|---|---|
| D1 新颖性 | 能指出此前**没有的构念或决策能力**；且该差异是**任务定义层面**的，不是精度/工程层面的 | 与最强近邻的方法论对照 |
| D2 显著性 | 失败类的**普遍性**与**后果**都可量化，且不是小众场景 | prevalence 估计 + 成本证据 |
| D3 构念效度 | 有形式定义 + 可操作测量 + 一致性/效度证据（人判需一致性；自动判需与真值相关） | 定义、编码规则、κ/α、效度相关 |
| D4 可证伪性 | 有明确的 **kill criterion**：什么结果出现就撤回主张 | 预注册式条款 |
| D5 证据强度 | 是**因果/机制**证据而非相关叙事；有强基线与负控 | 处理效应 τ、配对设计、消融、负控 |
| D6 基线可得性 | 最强对手**可获取、可复现**，且不是稻草人 | 可运行基线或对其任务定义的形式化分析 |
| D7 可复现性 | 数据/代码/预注册/失败案例齐备 | 制品与登记记录 |
| D8 生态效度 | 有**主场景**（单开发者 × 多会话）真实数据，或明确代理并报告全部威胁 | 数据来源与代理映射表 |
| D9 伦理与隐私 | 会话/提示含用户代码的处理方式已声明 | 数据治理条款 |
| D10 场景保真度 | 忠于 §1.1 主场景，未偷换成"多 agent 自治协作" | 场景锚点一致性 |

### 判定规则（三档）

| 档位 | 条件（互斥且穷尽） | 含义 |
|---|---|---|
| **可投（研究轨）** | D1/D3/D5 三项中 ≥2 项为"强"，**且**无任何"未通过" | 具备顶会研究论文骨架 |
| **需降级** | 不满足"可投"，但"未通过"项 ≤1 | 降为工具轨 / 短论文 / 期刊（EMSE），或补强 D1/D3/D5 中至少一项 |
| **不可投** | "未通过"项 ≥2 | 先补地基，投出去会被 desk-reject 或被判"不构成贡献" |

判"强 / 部分 / 未通过"时，一律以 §6 的实测事实为准，不用"我们计划会做"来充抵。注意第二档同时覆盖两种情形：**有 1 项未通过**，或**无未通过但 D1/D3/D5 中不足两项为强**（即"没有硬伤但也没有足够硬的骨架"）。

## 3. 各方案逐维检验

### 方案 A：任务↔变更绑定丢失（Task–Change Binding Loss, TCBL）

**痛点重述（学术版）**

> 在单开发者并行开启多个 agent 会话的工作模式下，任务声明与代码变更之间的归属关系只存在于会话历史中，无法从仓库侧重建。当会话结束、窗口关闭或 agent 改写自身计划后，变更失去可核查的任务归属，使审查、去重与责任定位退化为考古式推断。

**构念与测量**

- 绑定 \(b(c_i)=\{t_i,s_i\}\)（任务 + 会话载体，见主文档 §4）；
- **绑定存活率** \(B=\dfrac{|\{c_i:\ \text{可从仓库侧重建 } b(c_i)\}|}{|C|}\)。

关键设计点：\(B\) 度量的是**信息在仓库中的可得性**，不是 commit message 质量。因此必须把 message 质量分作为**协变量**，并把"控制 message 质量后 P1 仍成立"设为方案的生死线。这是本方案区别于"写更好的提交信息"类研究的**唯一**防线。

**可证伪预测**

- P1：\(B\) 随会话并发度 \(N\) 单调下降；
- P2：\(B\) 低预测返工与集成延迟，效应在控制改动规模、文件数、message 质量后仍存在。
- **Kill**：若在控制 message 质量与 PR 描述质量后 \(B\) 不再随并发度下降，则撤回"版本控制缺少会话层"的主张，本研究降级为"开发者文档习惯"研究。

**所需证据**：① 多会话轨迹或明确的等价代理；② \(B\) 的可执行编码规则 + 双人一致性；③ 与 message 质量的分离实验。

**逐维检验**

| 维度 | 判定 | 依据 |
|---|---|---|
| D1 新颖性 | 部分 | 必须靠"控制 message 质量后仍成立"才站得住，否则与提交信息质量研究重合 |
| D2 显著性 | 强 | 主场景直接映射；返工/延迟成本可直接度量 |
| D3 构念效度 | 强 | \(B\) 定义清晰、单位明确、可用编码规则落地 |
| D4 可证伪性 | 强 | kill 明确且可执行 |
| D5 证据强度 | 中 | 可做剂量-反应（并发度→B→成本），但因果需受控/历史回放设计 |
| D6 基线可得性 | 强 | 基线是 `git blame` 与提交信息质量方法，均可复现 |
| D7 可复现性 | 强 | 可预注册；现有标注链路（包+校验+一致性脚本）可直接复用 |
| **D8 生态效度** | **未通过** | 仓库中没有任何多会话轨迹；Flask 代理是**不同人**的 PR，不共享会话（见 §6） |
| D9 伦理与隐私 | 中 | 会话含用户代码与提示，需治理条款；若只用公开仓库则为低风险 |
| D10 场景保真度 | 强 | 直接针对 §1.1 |

**预演反驳**

1. *"这不就是 commit message 质量研究？"* → 用分离实验回答（P1 在控制 message 质量后仍成立）。
2. *"\(B\) 会不会只是你主观判断？"* → 必须给编码规则 + 双人一致性，否则 D3 会掉到"部分"。
3. *"单开发者场景太小众。"* → 需要 prevalence 论证；可先用访谈/日志做规模估计。

**结论**：当前档位 **需降级**；唯一缺口是 D8，且这是一个**单点缺口**——补齐后 A 是五版里**最容易达标**的一版（其余 9 维无一项未通过）。

### 方案 B：可理解性侵蚀（Legibility Erosion, LE）

**痛点重述（学术版）**

> 同一代码实体被多个会话反复以**行为兼容**的方式修改后，其保留形态无法回溯到任何单一任务。该失败不伴随文本冲突，也不伴随行为或架构冲突，因此落在冲突检测的**任务定义之外**；其表现为"代码能跑、测试全过，但没人知道它为什么长成这样"。

**构念与形式化**

- 可回溯性 \(A(e)=\Pr[\text{审查者能把 } e \text{ 的保留形态映射到唯一有效任务}]\)；
- 侵蚀 \(LE(e)=1-A(e)\)；预测 \(LE(e)\) 随触碰数 \(k(e)\) 单调上升。
- 形式定义复用主文档 §4 的 **legibility break**：\(E_i\cap E_j\neq\varnothing\) 但 \(t_i,t_j\) 都不能单独解释合并后的语义。

**可证伪预测**

- P1：\(LE(e)\) 随 \(k(e)\) 上升（剂量-反应）；
- P2：**在 \(TC=BC=AC=no\) 的子集上 P1 仍成立**（这是与冲突研究的分界线，也是本方案的全部价值）；
- P3：维持任务↔变更绑定的治理层降低 \(LE\)（= 主文档 H6）。
- **Kill**：若 \(LE\) 与 \(TC/BC/AC\) 高度共现（共现矩阵显示不存在无冲突样本），或两名标注者无法一致判定 \(LE\)，则撤销该构念（主文档 H6 的撤销条款）。

**所需证据**：① 符号级反复触碰的正例；② 合成校准场景；③ 双人标注一致性；④ 人因测量（审查者回溯任务）；⑤ 共现矩阵证明独立性。

**逐维检验**

| 维度 | 判定 | 依据 |
|---|---|---|
| D1 新颖性 | **强** | 与 ConflictLens 一类的差异是**任务定义层面**的：其定义为"合并代码违反一个或两个分支的规格"（原文摘录：`02_相关工作与文献/相关工作原文证据摘录.md:16`），属两两不兼容，故无冲突的归属稀释在其定义域外 |
| D2 显著性 | 中→强 | 概念上很打动人，但**必须先有 prevalence**；当前为 0 |
| **D3 构念效度** | **未通过** | 构念尚未校准：7 个候选上 `LF` 全部不可判定，`gateA-pilot` 也没有 `LF` 场景（§6） |
| D4 可证伪性 | 强 | 共现矩阵即 kill，且已写进预注册 §6 |
| D5 证据强度 | 中 | P2/P3 需要人因实验才能支撑，否则只是相关性 |
| D6 基线可得性 | 中 | 基线是既有冲突检测器；定义域分析可行，但重实现成本高 |
| D7 可复现性 | 中 | 预注册与降级规则已就位，但 `LF` 无校准证据 |
| **D8 生态效度** | **未通过** | 同 A，且额外需要"同一符号被 3+ 变更触碰"的样本，现有候选一个都没有 |
| D9 伦理与隐私 | 中 | 同 A |
| D10 场景保真度 | 强 | 直接针对原始痛点的第一条 |

**预演反驳**

1. *"这不就是代码理解 / 认知负荷的旧问题？"* → 必须论证**新因**：会话并发 + 任务绑定丢失，而非一般可读性。
2. *"\(A(e)\) 太主观。"* → 需要可操作测量协议 + 一致性 + 与客观代理（触碰数、任务可解释比例）的相关性。
3. *"无冲突的反复修改本来就该重构，不算失败。"* → 需接上成本证据（返工/延迟），即把它接回 ACCD。

**结论**：当前档位 **不可投**（D3、D8 双未通过）。但它的 D1 是五版里最强的——正确用法是作为**新颖性钩子**与其他版本合并，而不是单独首发。

### 方案 C：ACCD + ISCC 协调层（现方案）

**痛点重述（学术版）**：多会话 agent 开发下，变更缺少任务、意图、语义影响、来源与生命周期信息，团队在理解、去重、验证、重构与集成阶段必须付出可观测的额外成本。

**逐维检验**

| 维度 | 判定 | 依据 |
|---|---|---|
| D1 新颖性 | 部分 | 已有五维构念 + 定义域差异可作差异化点；但仍需持续回答"是否只是 issue tracker / PR / 代码图 / LLM 摘要的重新包装"（主文档 §29） |
| D2 显著性 | 强 | 五维构念覆盖五类现象，且已建立覆盖完整性约束（§24↔§33 双向覆盖） |
| D3 构念效度 | 中 | 五维定义清晰，但 `M_legibility` 无任何校准证据 |
| D4 可证伪性 | 强 | Gate A–D + H6 撤销条款 |
| D5 证据强度 | **强** | 已有因果估计对象 \(\tau\)、并行度约束 \(\tau_{parallel}\)、配对设计、负控、机制链（§34–§37） |
| **D6 基线可得性** | **未通过** | 必须纳入 ConflictLens 等等价检测器与人工协调基线，**尚未实现**；当前无任何可运行基线。这是"基线过弱"风险的实质（§29） |
| D7 可复现性 | 强 | 预注册、降级规则、包生成/校验/一致性脚本、回归测试俱在 |
| **D8 生态效度** | **未通过** | 无真实多会话数据 |
| D9 伦理与隐私 | 中 | 需声明模型调用日志处理 |
| D10 场景保真度 | 强 | 已按 §1.1 收敛 |

**预演反驳**

1. *"已有 ISCC 式表示（issue 链接、PR、code provenance graph）。"* → 必须给出"新增的**决策能力**"实验，不能只讲表示层差异。
2. *"收益可能来自禁止并行。"* → 已有 \(\tau_{parallel}\) 约束，这条已预先堵住，是加分项。
3. *"任务登记负担。"* → 主场景下负担显著更低（§29 已注明），但**必须实测**。

**结论**：当前档位 **不可投**，但它是**承载机制与系统贡献的最佳容器**（D5 强、D7 强）。它同时依赖 D6 与 D8 两项外部条件，因此适合作为**第二篇/长文**，而非首发。

### 方案 D：冲突检测的任务定义覆盖缺口（Coverage Gap）

**痛点重述（学术版）**

> 主流"语义冲突"任务把失败限定为**两个变更之间的不兼容**。但在多会话开发中，一大类失败——反复的兼容修改导致的语义归属稀释——不含任何两两不兼容关系，因此在**定义上**落在既有检测方法的覆盖面之外。问题不是检测精度不够，而是任务定义不完备。

**形式化**

- 既有任务定义 \(\mathcal{T}_{conflict}=\{(c_i,c_j): \text{incompatible}(c_i,c_j)\}\)；
- 缺口类 \(\mathcal{T}_{legibility}=\{(c_1,\dots,c_k),\ k\ge3:\ \text{pairwise compatible}\ \wedge\ \nexists t\ \text{能解释 } e\}\)；
- 命题：在 \(TC=BC=AC=no\) 的子集上，**任何**形如 \(\mathcal{T}_{conflict}\) 的检测器召回恒为 0。这是**分析性结论**（由定义域直接推出），不是精度比较。

**为什么这个命题可被验证且有据可依**：已核对的 ConflictLens 把 semantic merge conflict 定义为"合并代码违反一个或两个分支的规格"，并在候选生成阶段**先丢弃文本冲突场景**、再以自动合并树与开发者合并树的差异筛候选（`相关工作原文证据摘录.md:16,20`）。这两个环节都要求"分支对之间的不兼容/树差异"存在，因此该类方法对 `pairwise compatible` 的反复触碰**没有输入**。这使 D1 成为可被审稿人直接检验的对照，而不是修辞。

**可证伪预测**

- P1：定义域结论（分析性，可构造性证明）；
- P2：\(\mathcal{T}_{legibility}\) 在真实历史中**非空且可被独立判定**（经验性）；
- **Kill**：若 \(\mathcal{T}_{legibility}\) 在真实数据中近乎为空（prevalence 极低），缺口虽真实但不显著，主张降级为"定义澄清"。

**所需证据**：① 对 2–3 个既有方法的**定义域分析**（低成本，**不依赖缺失数据**）；② \(\mathcal{T}_{legibility}\) 非空的经验证据（与 A/B 共用数据）；③ prevalence 估计。

**逐维检验**

| 维度 | 判定 | 依据 |
|---|---|---|
| D1 新颖性 | **强** | 定义域差异是审稿人最易接受、也最易被检验的"新" |
| D2 显著性 | 部分 | 完全依赖 P2 的 prevalence，**当前未测** |
| D3 构念效度 | 中 | 缺口类的形式定义清晰，但其经验判定借用 A/B 的构念 |
| D4 可证伪性 | 强 | P2 即 kill |
| D5 证据强度 | 中 | 定义域部分是分析性的；经验部分待测 |
| D6 基线可得性 | **强** | 可直接分析既有方法的任务定义，无需重实现 |
| D7 可复现性 | 中 | 分析可复现；经验部分依赖数据 |
| D8 生态效度 | 部分 | **定义域分析不需要多会话数据**（当前唯一可立即执行的部分）；prevalence 部分受 D8 限制 |
| D9 伦理与隐私 | 低风险 | 定义域分析不涉及私有数据 |
| D10 场景保真度 | 强 | — |

**预演反驳**

1. *"这是显而易见的，不算贡献。"* → 用形式化 + 对既有方法定义域的系统分析证明它**尚未被明确化**，并量化后果。
2. *"只批评不解决。"* → 必须同时给出缺口类的可操作定义与测量（即带上 A/B 的产物），哪怕解决方案留待后续。

**结论**：当前档位 **需降级**；但它是**当前唯一可以立刻开工**的一版——定义域分析部分不依赖任何缺失数据。建议作为首发论文的**贡献 1 与引子**。

### 方案 E：会话级来源与可审计性（Session-level Provenance）

**痛点重述（学术版）**

> 开发者需要回答"这段代码是在哪个会话、哪个任务、哪次尝试下产生的"，但现有版本控制与 agent 工具都不保留"会话"这一层，导致代码审查与责任定位不可行。

**逐维检验**

| 维度 | 判定 | 依据 |
|---|---|---|
| D1 新颖性 | 中 | 会话级 provenance 已被 prompt/agent trace 工具部分覆盖，需论证增量 |
| D2 显著性 | 强 | 可审计性在合规与团队协作中是硬需求 |
| D3 构念效度 | 中 | 需定义并测量"可审计性" |
| D4 可证伪性 | 中弱 | 人因研究的 kill 较软 |
| D5 证据强度 | 强 | 访谈 + 日志的混合方法可支撑 |

## 5. 推荐组合策略

不要五选一。按"钩子 + 构念 + 测量 + 容器"分工：

| 角色 | 承担方案 | 理由 |
|---|---|---|
| 新颖性钩子 | **D** | D1 强、D6 强，且可立刻开工，是审稿人最容易接受的"新" |
| 核心构念 | **B**（LE） | D1 最强，且是原始痛点第一条的正统学术化 |
| 测量与 prevalence | **A**（TCBL） | D3/D4/D7 强，是唯一能快速产出可报告数字的一版 |
| 机制与系统容器 | **C**（ACCD/ISCC） | D5 最强，承载 \(\tau\)、消融、负控与在线治理 |
| 人因线（并行） | **E** | 补 H4，独立投稿 |

**推荐的首发论文骨架（ICSE / FSE 实证轨）**：

> 以 **D** 为引子提出定义域缺口 → 以 **B** 为构念把缺口类形式化 → 以 **A** 的绑定存活率与 prevalence 做测量 → 以 **C** 的治理层做机制验证（保留给第二篇或本文的"初步系统"）。

这样排的好处是：即使系统效果不显著，前两层（定义域 + 构念 + 测量）**本身就构成一篇成立的经验论文**，而不会因为在线治理失败而整篇崩掉。

**必须先补的两项（与外部数据无关，现在就能做）**：

1. **D 的定义域分析**：对 ConflictLens 一类方法的任务定义与候选生成环节做形式化分析，写成可复现的分析脚本或文档；
2. **`LF` 的合成校准场景**：`gateA-pilot` 当前没有任何 `LF` 场景（§6），补进去才能让 B 的 D3 从"未通过"变成可判定。

## 7. 对"迭代痛点"的净结论

原始观察"AI 来了 Git 跟不上"在被迭代成学术命题的过程中，实际产生了**五个可分辨的候选**，而不是一个。其中：

- 学术上**最强、最诚实**的版本是 **D + B**：它不宣称 Git 失效，而是指出**既有失败分类法（语义冲突）存在定义域缺口**——这是一个可被形式化、可被既有方法检验、且审稿人难以反驳的贡献；
- **最容易先出成果**的版本是 **A**：唯一"未通过"项是 D8，其余 9 维无硬伤（但 D1 为"部分"，必须靠"控制 message 质量后 P1 仍成立"的分离实验撑住）；它也是唯一一版的测量可以直接复用现有标注链路。
- **最需要一个系统来承载**的版本是 **C**：证据设计最完备，但依赖强基线与数据两个外部条件；
- **E** 应作为独立的人因线，不要塞进技术论文里稀释主张。

必须明确写进论文的**边界**（否则会被一审打回）：本研究的场景是"单开发者 × 多 agent 会话"，其结论**不得**外推到"多 agent 自治协作"；且"Git 跟不上 AI"只是动机表达，不是本文结论——本文只检验"在 Git 之上增加任务中心协调层是否改善协同结果"。
