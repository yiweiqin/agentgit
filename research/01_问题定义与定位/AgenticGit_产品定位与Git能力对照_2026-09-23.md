# AgenticGit：评论分析、产品定位与 Git 能力对照

日期：2026-09-23。性质：产品需求与设计建议，不是已实现功能说明，也不是实证研究结论。

## 1. 客观结论

**痛点存在，但准确名称是“高速并行 agent 开发的持续协调负担”。其中直接覆盖文件、分支混乱等一部分可以通过正确使用 Git/worktree 明显缓解；任务重复、接口漂移、过期上下文、未提交成果不可见、归属追踪和集成准备仍需要额外协调。**

评论不是一边支持、一边完全否定。许多反对者实际上给出了解法：worktree 隔离、架构解耦、任务分工、汇总 agent、测试门禁、持续集成。它们说明已有可行实践，也说明有人需要持续执行这些实践。你的产品机会是将这套实践自动化、标准化，并让协调跟得上 agent 的动作速度。

因此不能把需求表述为“Git 已失效”，也不能把 worktree 描述成只有事后作用。worktree 在开工前就预防工作目录互相覆盖；预合并测试也可以在任务完成前运行。新的差异应落在：**对任务意图和依赖的早期判断、执行中持续更新、低成本面向 agent 的协调决策**。

用户已明确的定位：在 Git 基础上构建；主要使用者是高速 coding agents；目标是预防性措施；面向一人多会话以及多人多会话，尤其是管理流程不严格的小团队。Git 与 worktree 均为复用底座。

## 2. 评论逐条分析

评论编号按用户粘贴顺序，不根据统一显示的名字推断作者身份，也不将它们视为独立受访者统计。

| 编号 | 评论主要观点 | 合理部分 | 需要限定的部分 | 产品应吸收的设计 | 产品要证明的增量 |
|---|---|---|---|---|---|
| C1 | AI 增加代码/变更量，commit/history 意义降低 | 高频混合修改可能提高历史检索、理解和审查成本 | commit 的快照、恢复和追踪价值并未因此消失；意义降低是体验判断 | 自动保持任务与提交关系，提供任务级历史视图 | 相同 Git 历史上，定位意图/恢复正确状态更快、更准 |
| C2 | 每个 agent 用 worktree/分支，汇总 agent 合并 review；100 个分支也可以 | 技术上完全可行，是应认真比较的强基线 | 能容纳很多分支不等于无需协调；环境成本、重复工作、集成队列仍可能存在 | 自动分配隔离空间，复用汇总 agent，增加执行前和过程中的协调 | 比“worktree＋汇总 agent＋测试”少多少总返工，是否值得额外开销 |
| C3 | 从架构上解耦，避免并行开发同一模块 | 良好边界能从源头降低风险，不能用工具代替架构设计 | 遗留系统、横切修改和共享契约使完全独立不总可行；同模块修改也未必冲突 | 以模块边界分配任务，按函数/契约细化作用域，支持必要的边界变更 | 不要求先重构全项目，也能在剩余耦合处降低协调负担 |
| C4 | 属于耦合/冲突问题，AI 合并也快；按需求选择隔离级别 | 将版本存储与工程协调分开很准确；合并 agent 应作基线 | 干净合并不保证业务兼容；解决冲突快不等于重复实现和后续验证没成本 | 分层隔离、影响分析、接口契约、组合验证 | 总完成时间/成本优于事后快速修复，而非只降低文本冲突数 |
| C5 | 独立 agent 做需求分析、分工和定期 review | 正面给出“协调者”的既有解法 | 敏捷/瀑布选择本身不解决秒级变更；一次分工会随执行漂移 | 持久化任务计划，事件触发更新，按需调用协调 agent | 相比通用 supervisor agent，持续状态与精确触发带来什么收益 |
| C6 | 功能责任细化、禁止越界、强解耦、全量测试后提交 | 责任边界和契约测试能减少误改 | 严格禁止越界会阻塞必要重构；测试通过只覆盖已有断言，不等于全量语义保证 | 软所有权、授权移交、范围扩张检测、契约测试与高风险审批 | 比粗粒度锁更少误阻塞，同时避免无意识越界 |
| C7 | 每天并行五六个 session，worktree＋dev 分支＋CI，不能不要 commit | 提供了实际多会话使用的自述，证明推荐实践可用 | 自述不能量化普遍性；共享 dev 分支不会天然始终可用，仍依赖门禁与流程 | 保留 commit、dev 分支和 CI；自动准备并验证集成 | 对已有熟练工作流是否仍有收益；无收益人群不必强行覆盖 |

综合判定：这些评论支持“场景真实、已有办法、执行这些办法存在成本”，但不足以证明“多数团队都痛”或“必须引入新系统”。最可能受益的是并行度较高、任务存在共享接口/横切依赖、会话经常交接、人工协调能力不足的小团队。低并行、强模块化且现有流程稳定的团队收益可能很小。

## 3. 产品定义与能力边界

> AgenticGit 是基于 Git 的 coding-agent 预防性协调层：在 agent 接收任务、制定计划、修改代码、恢复上下文和准备集成时，维护任务—代码—契约—验证之间的关系，识别可避免的重复和干扰，向 agent 提供可执行的协调动作，并利用 Git/worktree/CI 保存、隔离、验证与集成成果。

主要使用者是 agent：接口应优先提供结构化 CLI/API、明确状态码、稳定任务标识、增量变更通知和可重试操作。人主要处理高风险架构取舍和目标冲突，而不是逐条批准普通写入。

Git 负责内容与历史的事实；协调账本负责任务、声明的意图、依赖和决策事实；测试负责其覆盖范围内的可执行验证。自然语言意图不是代码行为的绝对真值。

## 4. 完整能力对照表

来源：U=用户帖子与本轮明确要求；C1–C7=上述评论；D=基于这些需求补充的设计。优先级：P0=最小闭环；P1=增强；P2=后续；复用=保持底座原能力。以下“新增能力”均为目标设计，不表示已实现。

### A. 仓库、隔离与执行环境

| ID | 能力 | Git / worktree 现有能力 | 高速 agent 下尚需协调什么 | AgenticGit 新增能力与辅助方式 | 时机 | 来源/优先级 |
|---|---|---|---|---|---|---|
| A01 | 初始化/克隆 | init/clone 建立仓库与历史 | 会话不知道项目协调规则 | 检测仓库、注册协调配置、读取模块/测试约定；不改对象格式 | 接入 | U,D/P0 |
| A02 | 分支创建 | branch/switch -c 建分支 | 分支名不等于完整任务身份 | 为任务分配稳定 ID，映射分支、agent、工作树和基线 OID | 开工 | C2/P0 |
| A03 | 工作目录隔离 | worktree 提供不同工作目录与索引，共享仓库对象和大部分引用 | agent 可能被启动在错误目录 | 自动创建/绑定工作树，执行前核验工作目录与任务身份 | 启动/写入 | C2,C7/P0 |
| A04 | 隔离级别 | 可用 worktree、独立 clone；进程/容器隔离属于外部设施 | 文件隔离不隔离端口、数据库、环境和外部服务 | 根据任务选择工作树、独立 workspace 或容器；登记共享资源 | 启动 | C4,D/P1 |
| A05 | 同一分支检出保护 | worktree 默认限制同一分支在多个工作树同时检出 | 不同分支仍可能执行重复任务 | 保留 Git 保护，另查任务目标重复 | 分配 | C2/P0 |
| A06 | 工作树登记/清理 | worktree list/remove/prune/move/repair 管理目录关联 | 活跃任务目录可能被误清理，退出 agent 也可能遗留成果 | 活跃租约、任务结束确认、可恢复归档后建议清理 | 退出/维护 | C2,D/P1 |
| A07 | worktree lock | 防止工作树管理信息被 prune，非源码编辑锁 | 易误以为已获得代码互斥 | 不用它冒充代码锁；实体预约在协调层实现 | 作用域预约 | D/P0 |
| A08 | 多人多机器 | Git 通过远端分发已提交对象与引用 | 未提交意图和在飞计划不随 fetch 自动出现 | 共享协调服务与命名空间，支持跨进程订阅与重启恢复 | 全程 | U/P1；本机跨进程P0 |
| A09 | 网络中断 | 本地 Git 能继续工作 | 全局协调状态可能陈旧 | 带版本/有效期的本地缓存；独立工作可继续，高风险共享修改降级处理 | 断连/恢复 | D/P1 |

### B. 任务、计划和共享契约

| ID | 能力 | Git / 常见配套能力 | 尚需协调什么 | AgenticGit 新增能力与辅助方式 | 时机 | 来源/优先级 |
|---|---|---|---|---|---|---|
| B01 | 任务登记 | 分支名、message、外部 issue 可描述任务 | 缺少统一机器可读目标 | 任务卡记录目标、验收、约束、负责人和预期作用域 | 接收任务 | U,C5/P0 |
| B02 | 开工前去重 | search/log 可查已存在内容；Git 不判自然语言目标等价 | 其他 agent 的未完成能力不可见 | 查询已有/在建能力；建议复用、合并任务或保留差异 | 计划前 | U,D/P0 |
| B03 | 模块分工 | 外部文档、CODEOWNERS、人工规则可声明责任 | 规则不自动分配运行中会话 | 按模块边界建议任务分配，保留人工/协调 agent 的选择 | 分工 | C3,C5,C6/P0 |
| B04 | 共享子任务 | 分支不表示“两个任务共同依赖一个能力” | 两边各造一份公共组件 | 建共享子任务与唯一主实现，其余消费契约 | 开工/范围变化 | C2,C3,D/P1 |
| B05 | 依赖顺序 | Git DAG 表示提交祖先，不等于任务依赖 | 提交顺序不能表达未来接口依赖 | 任务依赖 DAG、生产者/消费者约定、就绪通知 | 计划/执行 | C5,D/P0 |
| B06 | 接口契约 | 类型、测试、文档可表达约束，执行由工具承担 | 尚未实现的跨任务接口需要先协商 | 发布 API/schema/配置/业务不变量契约并标版本 | 计划确认 | C3,C6/P0 |
| B07 | 范围预约 | Git 没有一般性的函数级任务预约 | 文件锁太粗，完全无约束又易误改 | 文件/符号/接口的软预约，含理由、租期和共享规则 | 写入前 | C6,D/P0 |
| B08 | 修改范围扩张 | diff 能反映已经发生的变化 | agent 执行中改变计划未通知别人 | 比较计划与实际 diff，触及新共享范围时重新协调 | 计划变化/写入 | U,C5/P0 |
| B09 | 目标改变/取消 | 可追加提交或删除分支 | 其他任务仍依赖旧目标 | 版本化任务卡，广播取消/替代，释放预约，重评依赖 | 目标变化 | D/P1 |
| B10 | 黑盒边界 | 模块边界、公开 API、测试约定存在于代码和流程 | agent 可能无意越界修改内部实现 | 默认通过公开契约协作；必要越界走移交/联合任务 | 修改边界 | C6/P0 |

### C. agent 执行中的预防措施

| ID | 能力 | Git / 现有工具能力 | 尚需协调什么 | AgenticGit 新增能力与辅助方式 | 时机 | 来源/优先级 |
|---|---|---|---|---|---|---|
| C01 | 即时状态 | status/diff 展示各工作树文件状态 | 缺少全局任务与未提交成果视图 | 汇总“谁准备改/正在改/已完成什么”，按权限提供增量摘要 | agent查询/订阅 | U/P0 |
| C02 | 同文件并行 | worktree 防直接覆盖，merge 可合并兼容文本 | 同文件不一定冲突，不能全锁 | 结合符号、diff 与契约判断，只干预真实高风险重叠 | 写入前 | C2,C3/P0 |
| C03 | 跨文件影响 | 静态分析/类型检查/测试可发现部分依赖问题 | Git 文本合并不判调用契约 | 跟踪导出接口、schema 和关键调用依赖，通知消费者 | 契约变化 | C4,D/P1 |
| C04 | 陈旧上下文 | fetch 更新引用，不更新 agent 的推理假设 | agent 根据旧接口继续写 | 记录关键读取基线/契约版本，写入前检查是否仍适用 | 读取后/写入前 | U,D/P0（文件级） |
| C05 | 计划与写入竞争 | Git 自身索引/引用锁保护 Git 操作，不是任意 agent 计划事务 | 两个 agent 检查后仍可能同时行动 | 预约与校验使用版本号/CAS；必要时只短暂串行化热点动作 | 检查到写入间 | D/P1 |
| C06 | 进度可见 | 未推送/未提交内容通常不在远端主线 | B 不知道 A 已有可复用成果 | 共享能力状态和可验证 checkpoint，不默认广播完整代码/聊天 | 进度变化 | C2,C5/P0 |
| C07 | agent 交接/压缩 | Git 保存代码，聊天上下文不属于 Git 核心 | 恢复后忘记所有权和依赖约定 | 重建任务、契约、未完成决定及相关 diff 的最小上下文包 | 恢复/交接 | U,D/P1 |
| C08 | 结构化协调响应 | Git CLI 输出版本操作结果 | 普通告警未必改变 agent 行为 | 返回 allow/reuse/refresh/replan/wait/review，附依据与后续动作 | 决策点 | U,D/P0 |
| C09 | 提示与阻塞分级 | hooks/策略能阻止部分动作 | 全部阻塞会损失高速并行收益 | 默认建议；证据明确的破坏性契约冲突才局部阻塞 | 干预 | C4,C6/P0 |
| C10 | 消息负担 | Git 不负责跨 agent 消息压缩 | 高频全量广播占上下文与 token | 按依赖订阅、去重、批量合并，只给当前任务相关信息 | 高频事件 | U,D/P0 |
| C11 | shell/脚本改文件 | Git 事后可看 diff | 编辑工具 hook 可能漏掉 shell、生成器和外部编辑 | 工具包装＋动作后 diff 对账，记录覆盖范围；无法前置截获的不声称已预防 | 命令前后 | D/P0 |
| C12 | 崩溃/失联 | Git 可保留已有文件/提交，是否保存取决于执行情况 | 预约不释放、半成品无人接管 | 租约过期、任务 orphan 状态、checkpoint 接管与人工确认 | 心跳失效 | D/P1 |

### D. 暂存、提交与历史理解

| ID | 能力 | Git 原生能力 | AgenticGit 如何辅助 | 边界 | 来源/优先级 |
|---|---|---|---|---|---|
| D01 | 内容差异 | diff，含多种文本比较和统计 | 将实际 diff 映射到任务、实体和受影响契约 | 不把意图声明当行为证明 | C1/ P0 |
| D02 | 部分暂存 | add -p 等选择修改 | 提议按任务暂存，发现多个任务混入同一变更 | 交织且不可分的修改不强行拆开 | C1,D/P1 |
| D03 | 原子提交 | commit 保存快照、父关系和元数据 | 在任务检查点建立可回退提交并记录验证状态 | 保留 commit，不替代内容历史 | C1,C7/P0 |
| D04 | 提交粒度 | 由用户/工具选择 | 区分恢复用 checkpoint 与评审用任务提交 | 不是每次写文件都强制 commit | C1,D/P1 |
| D05 | 提交说明 | message、trailers、notes 可携带信息 | 绑定任务 ID、契约版本、验证证据引用和协调决定 | 大量动态状态不塞入每条 message | C1,D/P0 |
| D06 | 临时保存 | stash 保存部分工作状态 | 记录暂停原因和依赖，恢复前检查契约是否过期 | 不擅自把其他 agent 改动一起 stash | D/P1 |
| D07 | 修改提交/重写 | amend、rebase 等更改历史 | 更新旧新 OID 映射与任务关联 | 不默认重写已共享历史 | D/P1 |
| D08 | 丢弃修改 | restore/reset/clean 等具有不同作用 | 按任务展示影响范围、做可恢复检查点、保护其他任务成果 | 破坏性操作遵守现有权限与审批 | U,D/P0（保护） |
| D09 | 重命名/移动 | mv，diff 可推断重命名 | 更新实体与依赖关系，必要时重新索引 | 名称相似不是稳定语义身份 | D/P1 |
| D10 | 忽略与属性 | gitignore、gitattributes、过滤器、换行规则 | 尊重项目设置，将纯格式/生成物变化降噪 | 不修改底层 Git 语义 | D/复用 |
| D11 | 任务级历史 | log/show/blame/pickaxe 查内容历史 | 额外支持“为何改、为谁改、哪些 agent 共同形成结果” | blame 最后修改者不等于全部责任人 | C1/P1 |
| D12 | 来源可审计 | author/committer/signatures 标记与验证来源 | 分别记录提出者、执行者、协调者、批准者 | 不伪造人工作者或自动签名授权 | U,D/P1 |

### E. 同步、合并、验证与发布

| ID | 能力 | Git / 配套能力 | AgenticGit 如何辅助 | 相对事后汇总的增量 | 来源/优先级 |
|---|---|---|---|---|---|
| E01 | 获取远端 | fetch 获取对象/引用 | 对变化做依赖影响路由，通知相关任务 | 提前发现假设变化 | C7,D/P0 |
| E02 | 同步分支 | pull/merge/rebase | 按检查点安排同步，同步后重验受影响契约 | 不在 agent 写到一半时盲目更新 | C7,D/P1 |
| E03 | 分支新旧 | 提交图可比较领先/落后 | 额外衡量关键契约是否陈旧 | 1 个破坏性接口提交可能比 10 个文档提交重要 | D/P1 |
| E04 | 预合并 | merge-tree、临时分支/工作树可模拟集成 | 风险触发或增量 checkpoint 上自动预合并 | 不等全部任务完成；复用既有能力而非宣称发明预合并 | C2,C4/P0 |
| E05 | 正式合并 | merge 执行合并 | 核对任务依赖、验证与预期成果，再调用 Git | 减少准备不足的集成 | C2,C7/P0 |
| E06 | 冲突解决 | Git 给出冲突，人工/agent 解决；rerere 复用记录 | 给解决 agent 双方目标、必须保留的约束和关联测试 | 让解决冲突有依据，而非只抹去标记 | C2,C4/P1 |
| E07 | 跨分支迁移 | cherry-pick/apply/am 搬运提交或补丁 | 检查目标基线与所需依赖，提示缺失部分 | 避免搬来半个能力 | D/P1 |
| E08 | 提交门禁 | hooks 可运行检查；不是全局不可绕过的安全边界 | 本地快速检查＋服务端/CI 权威检查，对应任务验收 | 不依赖 agent 自觉记得每次跑测试 | C6/P0 |
| E09 | 单元/契约测试 | 由测试工具执行，Git 不提供测试充分性保证 | 按影响范围选测试，关键契约变化扩大验证范围 | 降低漏测且控制每次全量测试成本 | C6,D/P0 |
| E10 | 组合行为验证 | CI 可测试合并结果，合并队列可检查候选 | 按任务依赖优先验证高风险组合 | 文本无冲突也验证接口/行为 | C4,C7/P1 |
| E11 | 集成顺序 | Git 执行给定顺序；队列/人决定 | 按依赖和就绪程度排序，避免消费者先于生产者 | 减少主 dev 分支反复修复 | C5,C7/P1 |
| E12 | 主分支健康 | 分支本身不保证健康，需保护规则、CI、评审 | 尊重门禁，错误不得标为 integrated，支持恢复策略 | 明确“合入”与“验证通过”的状态 | C7/P0 |
| E13 | 推送与评审 | push 更新引用；PR/review/CODEOWNERS 属托管配套 | 生成任务级摘要、预防动作与剩余风险，提交正常 PR | 保留既有团队协作入口 | C2,C7/P1 |
| E14 | 回归定位 | bisect 与测试定位问题提交 | 关联任务和契约变化，辅助定位组合性回归 | 提升恢复与诊断速度 | D/P2 |
| E15 | 回退/恢复 | revert、reflog 等支持不同恢复方式 | 展示依赖影响、同步更新协调状态和待办 | 防止代码已回退但账本仍显示能力可用 | U,D/P1 |
| E16 | 发布标记/导出 | tag/archive 等 | 输出完成任务、接口变化和迁移说明 | 保留 Git 发布事实，补任务解释 | D/P2 |

### F. 底层完整性与扩展能力

| ID | 能力 | Git / 生态现有能力 | AgenticGit 的关系 | 优先级 |
|---|---|---|---|---|
| F01 | 内容寻址与对象数据库 | blob/tree/commit/tag 对象与对象校验 | 完全复用，不建立竞争的内容真值源 | 复用 |
| F02 | 引用与操作锁 | ref 更新与索引操作有自身一致性机制 | 调用 Git 正常接口；任务预约不能取代 Git 锁 | 复用 |
| F03 | 对象维护 | gc/repack/prune/maintenance/fsck | Git 管对象；自身单独管账本索引、保留策略和垃圾清理 | 复用/P1 |
| F04 | 子模块 | submodule 固定子仓库版本 | 将跨仓库契约及版本联动建模为依赖 | P2 |
| F05 | 稀疏检出/部分克隆 | sparse-checkout/partial clone 减少可见文件/对象 | 标出分析覆盖范围，按需读取；不假装已扫描全仓 | P2 |
| F06 | 二进制/大文件 | Git 可跟踪二进制，LFS 属扩展生态 | 对不能语义合并的对象采用预约/所有权和外部验证 | P2 |
| F07 | hooks/自定义合并驱动 | 提供扩展入口 | 作为部分接入点；任务/写入级事件需 agent 宿主集成或工具包装 | P0 |
| F08 | 权限与认证 | 托管服务器、系统权限与凭据控制访问 | 不扩大 agent 原权限；意图查询也遵守项目可见范围 | P0 |
| F09 | 外部编排与协议 | CLI/API、MCP 等可以暴露工具接口 | 支持 agent 调用，但 MCP 是接口形式，不是冲突预防算法 | CLI P0，其他P1 |
| F10 | 非接入参与者 | Git 允许普通开发者直接提交 | 定期 diff/fetch 对账发现外部变化；区分“已观测”与“已协调” | P0 |

本表覆盖主要能力族，不把每个 plumbing 子命令机械扩成产品功能。底层能力以复用为主；与任务、意图、依赖和实时执行有关的部分才是新增产品价值。

## 5. agent 专用的交互与决策协议

建议概念接口如下，名称仅为设计草案，尚非现有可执行命令：

| 概念动作 | agent 输入 | 系统输出 | Git 关联 |
|---|---|---|---|
| task register | 目标、验收条件、基线、负责人 | task ID、重复候选、工作树 | 创建/绑定分支与工作树 |
| plan publish | 作用域、读写接口、依赖、拟改变的契约 | 兼容性判断、共享子任务建议、预约版本 | 不直接修改代码 |
| context refresh | task ID、当前基线、已知契约版本 | 与本任务相关的最新变化 | 可关联 fetch/diff |
| change preflight | 目标实体、拟改变行为、预期基线版本 | allow/reuse/refresh/replan/wait/review、原因及有效期 | 写入前决策 |
| change reconcile | 动作后 diff、成功/失败、真实修改范围 | 更新作用域和影响通知 | 读取实际 diff，补漏记 |
| checkpoint | 完成片段、验证结果 | 可恢复快照、能力状态 | 提交到任务分支 |
| integrate prepare | 任务成果、依赖版本、验收证据 | 预合并/测试结果、剩余风险 | 临时集成树与 CI |
| task finish/cancel | 完成或取消原因 | 释放预约、更新依赖者、归档记录 | 合入/保留/清理建议 |

低延迟路径先做身份、版本、路径和已知依赖检查；只有不确定且有实际风险的情况才调用模型判断。缓存键应包含相关 Git OID、契约版本与任务状态，避免对过期分析复用结论。评估预防性能时记录 p50/p95 延迟、额外 token、误阻塞时间和漏检。

任务状态可为 proposed→active→validated→integrated，另有 paused/abandoned/superseded。运行状态应另记 executing/waiting/idle，避免把“没有合入”误当成“正在并行执行”。

## 6. 一条完整的产品场景

开发者甲让 A 增加登录，开发者乙让 B 增加权限校验。A、B 各自在 Git worktree 中工作。

1. 两者登记任务。系统发现都需要解析用户身份，提出共享身份解析子任务，而不是仅因修改同文件而报警。
2. 确认 A 提供 `resolveIdentity()` 契约；B 根据契约和测试替身开发权限逻辑。两者继续并行。
3. A 发现接口需要异步化，发布契约变更。系统定位 B 的依赖，在 B 继续写入同步调用前通知它更新计划。
4. A、B 分别建立 Git checkpoint。系统检查实际 diff 是否符合声明，发现额外越界修改则补协调。
5. 系统在临时集成树进行预合并与契约测试。即使文本合并干净，也验证调用行为。
6. 汇总 agent 接收双方验收条件和测试结果，通过既有 PR/CI 流程合入 dev 分支。

相对“先各做完，再汇总 agent 合并”，节省的是重复解析器、过期调用方实现和相关返工。若直接事后修复更便宜，则此场景没有证明产品净收益。

## 7. MVP 范围与判定产品是否值得做

首版建议仅实现：任务/工作树绑定、跨进程持久状态、开工前重复候选提示、文件/接口级软预约、基线陈旧提醒、动作后 diff 对账、agent 结构化通知和预合并测试。以本机多人会话拓扑可复现的场景先跑通，再扩展跨机器。

暂不承诺：任意语言全语义分析、所有冲突提前发现、自动修复所有业务冲突、所有 Git 操作完全自治、自动重构全项目实现极端解耦。

必须比较的产品基线：

| 基线 | 含义 | 为什么重要 |
|---|---|---|
| G1 | 每 agent 一个 worktree＋正常 commit＋汇总 agent＋CI | 直接回答 C2/C7 的“现成方案已经够用” |
| G2 | G1＋共享任务表/明确模块负责人 | 排除收益仅来自简单分工 |
| G3 | G1＋定期 supervisor agent review | 检验持续事件协调是否优于已有汇总机制 |
| G4 | G1＋粗粒度文件预约/锁 | 检验更精细协调是否减少误阻塞 |
| AG | 同样底座＋AgenticGit | 在一致模型、任务、资源约束下比较 |

主要看有效完成任务数、端到端时间、总 token/计算成本、人工介入时间和回归缺陷；另看重复实现量、被避免的返工、误报警/误阻塞、实际执行并发。所有臂都应计入汇总和修复成本。

既测故意设计的碰撞场景，也测独立任务、已经解耦良好的项目和轻负载。独立工作时额外负担很低，才能支持面向高速 agent 的产品定位。提前报警本身不是成功，报警之后节省的总成本才是。

## 8. 命名建议与话题定位

以下为定位建议，未核验包名、商标、域名或 GitHub 项目重名，也未根据实时热度榜断言某词是“最近最热”。

| 候选名称 | 传达什么 | 优点 | 风险/适用性 |
|---|---|---|---|
| **AgenticGit** | 为 agent 工作流增强 Git | 最贴合用户原意，适合产品与研究工作名 | 容易被理解为“AI 自动运行 Git 命令”；必须加预防性协调副标题 |
| **IntentGit** | 任务意图驱动的 Git 协作 | 指向核心数据模型，辨识度较好 | 不能独自表达多 agent 和执行中协调 |
| **GitSentinel** | 守护、监测 Git 工作流 | 预防意味明确 | 容易被理解为安全扫描或只做告警 |
| **GitSwarm** | 多 agent 群体协作 | 多 agent 联想直接 | 易误解为另一个编码 agent 编排框架 |
| **GitWeave** | 编织多条工作流/变更 | 适合强调并行成果协调 | 技术作用不如 AgenticGit 直观 |
| **VibeGit** | 面向 vibe coding | 易传播、亲近独立开发者 | 容易弱化严谨协作与研究定位，不建议作主名称 |

首选：**AgenticGit — Preemptive Coordination for Coding Agents, Built on Git.**

中文：**AgenticGit：基于 Git 的编码智能体预防性协调层。**

可作为传播话题的方向：agentic software engineering、多 agent coordination、context engineering、agent memory、spec-driven development、agent harness。这些分别对应用户对象、协作、选择性上下文、持久状态、接口契约和执行接入。只有实际实现相应机制时才使用；MCP 可作为接入方式，不能替代产品定位。

不建议名称堆叠为“Swarm MCP Memory Agentic Git”：会掩盖产品解决的问题，也不利于持续定位。

## 9. 可直接使用的介绍文字

> Git 和 worktree 已经提供可靠的版本记录与工作区隔离。但当多个 coding agents 高速并行开发时，任务分工、未完成成果共享、接口约定和执行中变化仍需要持续协调。AgenticGit 在 Git 之上维护任务、代码与契约的关系，在开工及修改过程中向 agent 提供去重、上下文更新和依赖协调建议，并复用 worktree、commit、预合并与 CI，使团队更容易保持可解释、可验证的并行开发流程。

一句话：**让 agent 在动手之前知道彼此，在执行之中持续协调，让 Git 更容易接住它们的成果。**
