## 决策日期

2026-09-14（初版）／ 2026-09-15（修订）

## 触发问题

原始直觉是“AI 的到来导致 Git 跟不上版本了”。经过对语义合并、SWE-agent、ChatDev 和 Git provenance 方向的核对，这个表述过于宽泛，也混淆了两个不同层次的问题：

- Git 的核心任务是持久化对象、比较状态、管理历史和支持合并；
- 多会话 agent 开发的新困难是任务分配、意图对齐、变更归属、重复抑制、语义影响协调和集成决策。

已有证据并不支持“Git 的历史记录或对象模型已经失效”。更可辩护的结论是：**Git 仍能作为底层版本存储，但 Git 原生工作流没有把 AI agent 协作所需的任务和意图信息作为一等对象。**

> **这次改判放弃了什么（必须一并记录）**：改判之后，本文不再把“Git 本身失效”当作研究对象或结论，
> 因此**论文不会去检验该表述本身**，只检验“在 Git 之上增加任务中心协调层是否改善协同结果”。
> 若未来需要支持“Git 抽象本身不足”这一更强命题，必须另设实验
> （例如测量任务↔变更绑定的丢失率如何随会话并发度增长），不能从现有设计推导出来。

## 研究定位决策

将研究对象从：

```text
AI-native replacement for Git
```

修正为：

```text
AI-native change coordination plane on top of Git
```

中文名称建议为：

> **面向多会话 agent 开发的任务中心代码变更协调层**

ISCC 是该协调层中的核心变更表示，而不是一个声称完全替代 Git 的新版本控制系统。

### 场景收敛（同日第二次决策）

同时把研究的主场景从“多 agent 自治协作”收敛为 **单开发者 × 多 agent 会话**
（定义见主文档 §1.1）。该收敛是忠实地回到用户的原始观察，并有三项后果：

1. **修复方向变轻。** 在原始场景里任务是开发者**已经声明**的，缺的是任务声明与变更之间的**持久绑定**，
   因此修复方案是登记 + 绑定 + 共享可见性 + 合并前风险提示，而不是设计 agent 间的自治协商协议；
2. **一个威胁消失。** “开发者是否愿意登记任务”这一生态风险（主文档 §29）在该场景下显著减轻，
   因为开发者本来就在会话中把任务说清楚了；若实测登记负担仍高，说明实现方式与场景不匹配；
3. **代理关系变薄。** Flask 试点的“不同人类作者的并行 PR”在主场景下是更弱的代理：
   两者共享“任务由人声明、协调者是人”，但不共享“同一人的多个会话”，且没有任何 agent 轨迹。
   因此结论必须限定在“并行变更流”层级（见 `preregistration.md` §2）。

多 agent 自治协作**不是**本研究的设定，其结论不得与本研究结果合并陈述（主文档 §1.2）。

## 为什么这一定义更强

1. **避免可被轻易反驳的技术断言**：Git 的对象存储、分支和三方合并依然有用；研究不需要证明它们“失效”。
2. **对应真实痛点**：用户遇到的不是历史无法保存，而是不知道哪个 agent 在做什么、变更是否重复、代码是否有归属以及怎样安全集成。
3. **缩小实现边界**：原型可以通过 Git hook、sidecar metadata、CLI 或服务实现，不需要重写 Git。
4. **允许兼容现有研究**：ConflictLens 可作为语义冲突检测组件；SWE-agent 和 ChatDev 可作为 agent 工作流来源；provenance graph 可作为来源建模基础。
5. **使因果主张可检验**：处理变量是“是否使用任务中心协调层”，结果变量是协调债务和集成成本，而不是“是否使用 Git”。

## 系统边界

### 研究范围内

- 任务登记、验收条件和预期语义实体；
- agent 变更的来源、父关系和证据链；
- 重复、重叠、依赖、矛盾和替代关系；
- 变更生命周期与未归属产物；
- merge 前风险提示和集成排序；
- 在不降低有效并行度下的协调成本评估。

### 明确不在研究范围内

- 替换 Git object database、SHA 哈希或基本持久化协议；
- 重新设计通用三方 merge 算法；
- 自动证明所有代码意图或所有语义冲突；
- 让系统完全替代人工代码审查；
- 只通过全局锁或禁止并行修改来降低冲突；
- 仅用 LLM 生成更长的 commit message。

## 修正后的核心研究问题

> 在开发者以多个 agent 会话并行修改共享代码库时，任务中心、意图作用域化且来源可追溯的变更协调层，能否在保持 Git 作为底层版本存储和保持有效并行度的前提下，降低 AI 变更协调债务与单位有效功能的集成成本——**包括在没有任何文本或行为冲突发生时，降低“反复修改后意义无法回溯”这一独立的失败类别**？

## 2026-09-15 修订：定位变更

用户明确选定新框架后，本记录中两处决策被推翻。**保留原文以备对照，此处记录变更与代价。**

| 被推翻项 | 原决策 | 新决策 | 代价 |
|---|---|---|---|
| §1「Git 仍能精准版本控制，缺的是任务层」 | 以"任务/意图元数据缺失"为根因 | 根因改为**调和吞吐失配**：\(\lambda\)（变更到达速率）持续超过 \(R\)（调和能力） | 必须**停止**说"Git 不够精准"（该说法可被一句话反驳），改说"其量级前提 \(\lambda\approx R\) 被打破" |
| §2「Git 之上的协调层」 | 不替代 Git，只加一层平面 | **代行 Git 工作流中人类调和职责的 agent** | 需精确界定"代行"的范围，明确不含对象存储与三方合并 |

**新根因的表述（取代"多智能体软件工程的任务分配"清单）**：

> 当多个开发者各自驱动多个具备**有界上下文**的 agent 并行修改同一代码库时，变更到达速率 \(\lambda\) 跃升若干数量级，而调和能力 \(R\)（为每个变更建立归属、验证后果、并入可解释状态）仍受人类审查约束。\(\lambda\approx R\) 是 Git 工作流的隐含设计前提，agent 打破了它。

**新制品的表述（取代"协调层"）**：

> **一个以 Git 为存储底座、代行其工作流中人类调和职责的治理 agent。** 它不重写 Git，它接管 Git 工作流**假定由人来完成**的那部分吞吐。设计立场是"用 AI 治理 AI"。

**这次修订的收益**（不只是妥协）：

1. 根因从**描述性**（"缺字段"）变为**因果性 + 技术必然性**（上下文窗口是硬约束）；
2. 得到可证伪的量化核心：\(\lambda/R\) 与其临界比；
3. 制品从抽象平面变为**有主体、可演示的 agent**，可传播性显著提高；
4. 此前几版的核心发现（意图稀释、绑定存活率）被**收编为后果**而非丢弃，理论被简化。

**新定位下的硬约束（不可违反）**：

- 任何以降低 \(\lambda\)（阻塞、串行化）换来的改善**都不算治理收益**（主文档 §34 的 \(\tau_{parallel}\) 与 H5 已为此预先设计）；
- 若 H3 不成立（agent 变更只是"量"的问题而非"质"的问题），理论贡献须主动降级，不得以"AI 原生"字样掩盖；
- **失效态不可由 Git 历史观测**（见 `痛点_速度与上下文失配.md` §10.3 的实测），因此必须新建 agent 侧观测通道，不能用"再找一批公开仓库"替代。

**"Git 跟不上 AI"这句话的最终处理**：仍**不**作为论文的技术命题（原判断正确），但它的**直觉被保留并精确化**——跟不上的是**调和吞吐**，不是精度。这个改写既不放弃用户的原始观察，也不留下可被一击反驳的语句。

## 取舍结论

后续实现和实验均以“协调层”作为系统边界，以“ACCD 下降”作为理论目标，以“Git compatibility”作为工程约束。若实验最终只证明离线语义风险检测有效，则成果应命名为 change risk analysis；只有当在线任务协调、来源治理和集成成本也得到证据支持时，才使用 change governance。
