# 面向多会话 agent 开发的 AI 原生版本控制：研究问题迭代稿

## 1. 研究定位

本项目研究的不是“给 Git 增加若干 AI 命令”，而是考察一个更基础的模型失配问题：当**一名开发者同时开启多个 agent 会话、把不同任务分别交代给它们**、这些会话并行修改同一代码库时，传统以 commit、snapshot、diff 和 branch 为核心的版本控制抽象，是否仍能充分表达和治理软件变更。

### 1.1 目标场景（构念的锚点）

本节固定研究的**主场景**，后续所有标签、指标和实验都必须能在这个场景里落地：

```text
一名开发者
  ├── 会话 1 → 任务 A → 改动共享代码库
  ├── 会话 2 → 任务 B → 改动共享代码库
  └── 会话 N → 任务 N → 改动共享代码库
        （任务由开发者用自然语言声明，协调者是开发者本人）
```

该场景有三个必须同时成立的特征，它们共同定义了本研究的适用范围：

1. **协调者是人**，不是 agent 之间的自治协商协议；
2. **任务是显式声明的**——开发者在会话里已经把它说清楚了，因此问题不是“任务无法表达”，而是“任务声明与代码变更的绑定只存在于会话历史中，落不到仓库里”；
3. **并行是真实的、共享工作树或共享分支空间的**，因此会话之间会互相踩到同一处代码。

### 1.2 与「多 agent 自治协作」的区分（重要）

“多个 agent 之间自主协商、互相调用”是另一类研究问题（ChatDev 一类工作已覆盖其通信与编排），**不是本研究的设定**。两者不可混用：

| | 本研究主场景：人 × 多会话 | 非本研究设定：agent 自治协作 |
|---|---|---|
| 协调发生在 | 人（会话之间手动分发） | agent 之间的协议 |
| 任务从哪来 | 人已声明，但绑定会丢失 | 需要协商产生 |
| 缺什么 | 任务↔变更的**持久绑定**、语义影响、来源与生命周期 | 协商协议、优先级与冲突消解 |
| 修复方向 | 轻：登记、绑定、共享可见性、合并前风险提示 | 重：协议、自治决策、多轮协商 |

本研究**只**主张前者的结论。若后续需要研究后者，必须作为独立场景另行报告，其结论不得与前者的结果合并陈述。

研究对象被定义为：**与 Git 兼容的、任务感知和意图感知的代码变更治理层**（AI-native change governance layer）。它在 Git 的文件版本历史之上增加任务、意图、语义实体、来源、依赖和验证状态等一等数据；工程形态可以是 Git hook、sidecar 元数据、CLI 或本地服务，**不需要重写 Git**。

## 2. 核心问题（收敛版）

### 2.1 现象

在 §1.1 的多会话场景下，开发者会遇到：

- **同一处代码被多个会话反复修改，最终无人能回溯其意义。** 每一次改动单独看都可能是合理的、行为兼容的，但叠加之后该处的语义归属被稀释：没人能说清它现在为什么长这样、由哪个任务驱动、改动之间是什么关系；
- 文本无冲突但行为相互干扰的语义冲突；
- 多个会话对相同目标进行重复实现；
- 同一领域概念出现多个名称或接口；
- 未提交文件和半成品在共享工作树中失去归属，无法判断哪些属于哪个会话；
- 为隔离修改而开出大量短生命周期分支，最终难以集成甚至直接废弃。

其中第一条有两个互相独立的子命题，本文分别处理，不得合并：

- **(a) 重复触碰**：同一处代码被多个会话反复修改；
- **(b) 可理解性侵蚀**：最终该处的意义无法被回溯到任何单一任务，维护成本上升。

(a) 只有在升级为冲突时才落进冲突类标签；**(b) 在行为兼容、无任何冲突的情况下同样会发生**，因此需要独立测量（见 §24 的 `M_legibility` 与 §11.1 的 `LF` 标签）。

### 2.2 根因

上述现象的共同根因不是 Git 缺少某个命令，而是两层缺失叠加：

**第一层：Git 的基本变更对象过于贫乏。** 传统变更主要表示：

```text
commit -> files -> textual diff
```

**第二层：任务声明与代码变更的绑定只存在于会话历史中。** 在多会话场景下，任务事实上**是存在的**——开发者已经把它写给了 agent。但这些声明停留在聊天记录里：会话结束、窗口关闭、agent 重试或改写自身计划之后，任务与它所产生的变更之间不再有可核查的连接，谁在什么意图下动了哪一处代码，事后无法重建。

一个完整的变更表示必须同时覆盖：

```text
task -> intent -> semantic entities -> change set -> provenance -> validation -> integration
```

前者记录“代码变成了什么”，后者还必须记录“为什么改、谁在改、与哪些任务相关、是否重复、是否已验证、能否安全集成”。**第二层缺失是本研究的直接靶点，也是“给 Git 做插件”这一工程直觉真正要补的东西。**

### 2.3 研究命题

> 在开发者以多个 agent 会话并行修改同一代码库时，把代码修改从孤立的文本差异提升为带有任务语义、变更意图、来源和生命周期的结构化变更对象——并保持任务声明与变更之间的可核查绑定——能否在保持并行度的同时，降低语义冲突、重复实现、**可理解性侵蚀**和集成债务？

这一定义把论文的因果主张限定为：**变更表示与治理机制的升级**是否改善协同结果，而不是笼统宣称“AI 会改变 Git”。

## 3. 最小研究系统（MVP）

为避免“大而全”，原型只实现一条闭环：

1. 开发者开始一个会话时登记结构化任务卡（目标、验收条件、预期代码实体），**并把会话标识绑定到该任务卡**，使绑定在会话结束后仍然可查；
2. agent 执行后生成带来源和意图的 change set；
3. 系统根据任务和语义实体进行重复任务检测；
4. 系统在合并前进行语义影响重叠分析；
5. 系统将变更标记为 proposed、active、validated、integrated、stale 或 abandoned；
6. 系统输出可解释的集成建议，而不是强制自动合并。

该 MVP 的核心不是替代 Git，而是在 Git 之上增加一个可审计的变更协调平面。

## 4. 形式化对象模型

对每个变更定义：

\[
  c_i=(t_i, s_i, a_i, E_i, I_i, P_i, V_i, L_i, T_i)
\]

其中：

- \(t_i\)：所属任务及验收条件；
- \(s_i\)：产生该变更的**会话标识**（会话是任务声明的载体；会话结束不解除绑定）；
- \(a_i\)：执行 agent；
- \(E_i\)：受影响的语义代码实体集合（函数、类、API、schema、配置键等）；
- \(I_i\)：变更意图及约束；
- \(P_i\)：来源、父变更和工具调用证明；
- \(V_i\)：测试、静态分析和人工审查结果；
- \(L_i\)：生命周期状态；
- \(T_i\)：该变更对同一实体已发生的**累积触碰序列**（用于可理解性判定，见 §33 的 \(M_{legibility}\)）。

定义两个变更的治理关系：

- 语义干扰：\(impact(c_i)\cap impact(c_j)\neq\varnothing\)，且二者的行为约束不一致；
- 任务重复：\(sim(t_i,t_j)>\tau_t\) 且验收目标高度重叠；
- 概念冲突：二者对同一规范概念产生不一致的命名或接口映射；
- **意图断裂（legibility break）**：\(E_i\cap E_j\neq\varnothing\) 但二者各自的 \(t_i,t_j\) 都不能单独解释该实体合并后的语义，即该处的最终形态无法回溯到任何单一任务；
- 可集成性：在满足依赖、验证和优先级约束时，二者可被合并。

## 5. 研究问题与可证伪假设

### RQ1：失效测量

在多会话 agent 开发中（§1.1 主场景），语义冲突、重复任务、意图断裂和集成债务的发生率是多少？它们与任务相似度、语义实体重叠、**同一实体的累积触碰次数**和会话并发度之间有何关系？

### RQ2：表示与检测

任务—意图—语义实体—来源表示，能否比文件级 diff 更准确地识别潜在冲突和重复工作？

### RQ3：治理效果

在不将所有任务串行化的前提下，变更登记、去重和生命周期治理能否改善最终集成结果？

### RQ4：人机协作成本

结构化来源和意图是否能够降低开发者理解变更、定位责任和解决冲突的时间？

对应假设：

- **H1（语义检测）：** 相比文件级 Git 冲突检测，语义影响分析能提高真实语义冲突的召回率，且在固定误报预算下保持更高精度。
- **H2（去重）：** 任务级相似性检测能降低重复任务执行率和重复实现率。
- **H3（并行治理）：** 使用治理层后，在相同 agent 并行度下，最终集成成功率提高、回归缺陷率下降。
- **H4（认知成本）：** 变更意图、来源和生命周期可视化能缩短人工审查和冲突解决时间。
- **H5（非退化并行性）：** 系统带来的协调收益不能仅由降低并行度获得；在控制有效并行度后，收益仍然存在。
- **H6（可理解性保持）：** 在没有行为冲突、也没有文本冲突的重复触碰场景中，维持任务↔变更绑定的治理层仍能降低该处的意图断裂程度，即在控制改动行数与行为不变量的前提下，事后标注者能把保留代码的语义回溯到有效任务的比例更高。

> 编号说明：本文的研究假设为 H1–H6。`03_基准与标注/benchmark/real-history/flask/git-history/annotation/preregistration.md` 中的
> H1–H9 是**另一套编号系统**，指标注流程的硬约束，两者互不指代；跨文档引用时必须写明来源文件。

H6 是本文相对既有语义冲突研究的**新增可证伪主张**：它针对的是“行为兼容但语义归属被稀释”的失败，而这恰是冲突类检测器定义上无法覆盖的部分（无 TC/BC/AC）。若 H6 不成立（意图断裂程度不随治理层下降），则 §24 的 `M_legibility` 维度与 §11.1 的 `LF` 标签应被撤销，不得保留为未测量却被声称的贡献。

## 6. 实验设计

### 6.1 基线

至少比较：原生 Git 分支、Git worktree、人工 Pull Request 集成，以及本系统的逐步消融版本（无任务卡、无语义实体、无来源、无生命周期治理）。

### 6.2 场景因子

- agent 数量：2、4、8；
- 任务相似度：低、中、高；
- 代码实体重叠：文件级、函数级、API/schema 级；
- 任务依赖：独立、链式、交叉依赖；
- 执行异步性：同步、随机延迟、长短任务混合。

### 6.3 主要指标

- 语义冲突 precision、recall 和 F1；
- 重复任务率、重复实现率；
- 概念/命名不一致率；
- 未归属工作区文件数及半成品比例；
- 分支数量、平均生命周期和废弃分支率；
- 集成成功率、合并后回归缺陷率和集成延迟；
- 人工审查时间、冲突解决时间和任务归属判断准确率；
- **意图断裂程度（`M_legibility`，对应 H6）**：同一实体的累积触碰次数、`LF` 标签比例、以及事后“保留形态→有效任务”的可回溯率；该指标必须在**无 TC/BC/AC** 的子集上单独报告，否则会被冲突类现象混淆；
- **任务↔变更绑定的存活率**：会话结束后仍可从仓库侧重建任务归属的变更比例（这是 §1.1 主场景的直接靶点指标）；
- 有效吞吐率：最终通过验证并保留的变更量 / 全部产生的变更量；
- 模型调用成本和单位有效功能成本。

## 7. 顶会级贡献边界

论文至少需要同时提供三类证据：

1. **经验贡献：** 首次或系统地刻画多会话 agent 开发的版本控制失效模式——**特别是“行为兼容但语义归属被稀释”这一冲突检测定义上无法覆盖的类别**——而不是仅展示个案；
2. **技术贡献：** 提出任务—意图—语义实体—来源—生命周期的变更模型及可运行原型；
3. **实证贡献：** 通过公开任务集、可复现实验和消融研究证明该模型在并行度不降低的条件下改善协同指标。

若只能完成其中一项，成果更适合定位为工具论文或设计报告，而不是顶会研究论文。

## 8. 下一轮迭代的决策门

在继续实现前，应优先验证三个问题：

1. 是否能从真实项目或构造任务中可靠标注“语义冲突”和“重复任务”；
2. 语义实体和任务意图的抽取误差是否会抵消治理收益；
3. 系统是否能保持并行开发能力，而不是通过强制串行化制造表面上的低冲突。

如果这三个问题没有可操作的答案，研究主张仍然过宽，不能进入顶会级系统实现阶段。

## 9. 与既有研究的边界

顶会论文必须说明本研究不是已有方向的简单拼接。相关工作可分为五类，但各自只覆盖问题的一部分：

1. **分布式版本控制与分支工作流**：擅长保存历史、创建隔离空间和检测文本冲突，但通常不表示 agent 的任务意图、语义影响和责任链。
2. **代码审查与 Pull Request 系统**：提供人工协作入口和审查记录，但通常在变更已经产生之后才介入，不能主动抑制重复任务或预测跨文件语义干扰。
3. **程序分析与合并冲突预测**：可以利用调用图、数据流或静态特征发现潜在冲突，但不一定知道两个变更是否服务于同一任务，也无法管理变更生命周期。
4. **多智能体编程框架**：关注任务分解、消息传递和 agent 编排，但代码库通常仍由 Git 以文件和分支为基本协调单位管理。
5. **数据/模型来源追踪与可复现系统**：强调实验或构建产物的 provenance，但未必把来源、意图和集成决策绑定到代码变更本身。

本项目的潜在差异化主张是：**以“可治理的变更对象”作为跨越上述层次的统一抽象，并在 Git 兼容边界内把任务级协调前移到代码修改发生之前。** 论文不能仅证明“LLM 能总结 diff”，而需要证明该抽象能够改变协作决策和最终集成结果。

## 10. 建议的核心机制：意图作用域变更胶囊

为了形成单一、可识别的技术贡献，建议将系统核心命名为 **Intent-Scoped Change Capsule（ISCC，意图作用域变更胶囊）**。每个胶囊至少包含：

```text
任务目标 + 验收条件 + 预期语义实体 + 约束/不变量
+ 实际变更 + agent 来源 + 证据链 + 验证状态 + 生命周期
```

ISCC 不等同于 commit：一个任务可以产生多个 commit，一个 commit 也可以被拆分为多个可独立治理的胶囊。胶囊之间建立以下关系：

- `overlaps`：语义影响范围重叠；
- `duplicates`：验收目标或实现目标重复；
- `depends-on`：一个胶囊需要另一个胶囊的接口或行为；
- `contradicts`：约束、不变量或设计意图不一致；
- `supersedes`：新胶囊替代旧胶囊；
- `validated-by`：由测试、静态分析或人工审查提供证据；
- `obscures`：两个胶囊先后触碰同一实体，且合并后的形态无法被任一方的任务卡单独解释（即 §11.1 的 `LF` 在胶囊层的关系表示；它**不要求**两者 `contradicts`）。

该机制的可检验预测是：如果胶囊关系足够准确，系统可以在 merge 前发现一部分 Git 无法检测的语义风险，并让开发者在更早阶段取消重复任务或调整修改范围。

## 11. 失效标签与标注协议

“语义冲突”不能由系统自己定义，否则会产生循环论证。建议建立公开标注协议：

### 11.1 标签定义

- **Textual conflict**：Git 三方合并直接产生冲突标记；
- **Behavioral conflict**：合并后至少一个已定义行为、测试断言或 API 契约被破坏；
- **Architectural conflict**：变更违反模块边界、依赖方向或项目级不变量；
- **Redundant task**：两个任务的验收条件在人工审查后被判定为实质重叠；
- **Redundant implementation**：不同变更实现了同一能力，且最终只保留一份；
- **Conceptual conflict**：两个变更针对同一规范概念、业务状态或接口语义使用不一致的名称、类型、生命周期或约束，导致维护者无法把它们视为同一抽象；
- **Legibility failure**：同一实体被多个会话反复触碰后，其保留形态无法回溯到任何单一有效任务；**即使行为兼容、无任何文本或行为冲突**，只要该处的语义归属已被稀释即成立；
- **Unowned artifact**：文件或代码片段无法映射到有效任务、agent 和生命周期状态；
- **Integration debt**：变更虽未立即失败，但需要额外返工、回滚或人工重构才能进入主线。

其中 `Legibility failure` 与四个冲突类标签（TC/BC/AC）**互斥无依赖**：前者描述的是“反复修改导致意义流失”，不是“两个改动之间不兼容”。因此不能因为 `TC = no` 或 `BC = no` 就判定 `LF = no`——这会把“未冲突”误读为“未侵蚀”，与 §33 的测量设计相冲突。


### 11.2 标注流程

每个样本由至少两名具有软件工程经验的标注者独立判断；冲突样本由第三名标注者裁决。报告 Cohen's kappa 或 Krippendorff's alpha，并公开标签定义、示例、裁决规则和匿名化样本。评估检测器时，测试集标签必须在系统预测之前冻结。

### 11.3 样本单位

样本不应只取一对 diff，而应保留完整上下文：任务描述、agent 对话摘要、基线提交、并行变更、测试结果、合并结果和后续修复。这样才能区分“检测到了文本重叠”和“预测到了真实协作失败”。

## 12. 可复现基准的两条轨道

### 12.1 历史回放轨道

从公开仓库抽取 issue、Pull Request、commit 和测试记录，重建当时的并行任务与集成顺序。该轨道具有真实代码和真实演化背景，适合评估失效测量与离线检测。

### 12.2 受控生成轨道

在固定版本的项目上生成任务组合，系统控制任务相似度、实体重叠、依赖结构和 agent 延迟。每个场景运行多个随机种子，并保存模型版本、提示词、工具调用和环境信息。该轨道适合做因果比较和消融实验。

两条轨道必须分开报告：历史回放提供生态有效性，受控生成提供内部有效性。不能用合成任务的结果单独宣称真实项目收益。

## 13. 统计分析计划

主要结果应预先注册或至少在实验前固定：

- 主要终点：语义冲突召回率、重复实现率、集成成功率、集成延迟和人工解决时间；
- 次要终点：分支碎片化、工作区污染、**意图断裂程度（`M_legibility`）**、模型调用成本和有效吞吐率；
- 使用分层 bootstrap 或混合效应模型，将项目、任务和随机种子作为随机效应；
- 报告效应量和 95% 置信区间，而不仅是 p 值；
- 多个指标和多个消融比较采用适当的多重比较校正；
- 对 H5 单独报告并行度、有效任务完成量和系统阻塞时间，排除“少做任务所以少冲突”的替代解释。

如果样本量不足以支持统计结论，应明确定位为探索性研究，而不能使用“显著提升”等确认性措辞。

## 14. 有效性威胁与应对

### 构念有效性

“意图”“语义冲突”和“有效变更”具有主观性。应使用任务验收条件、测试/契约违反和双人标注的组合定义，避免只依赖 LLM-as-a-judge。

### 内部有效性

不同 agent 的模型能力、提示词和工具权限可能成为混杂变量。应固定模型与工具配置，使用配对任务、随机种子和逐步消融。

### 外部有效性

小型项目或合成任务可能低估真实仓库的架构复杂度。应同时覆盖不同语言、项目规模、测试成熟度和任务类型，并公开失败案例。

### 生态有效性

研究原型的提示开销或人工登记步骤可能改变 agent 行为。应测量登记成本，并设置“轻量登记”和“完整登记”两种配置。

### 自动化偏差

如果系统的语义解析器与评估器使用同一个模型，可能出现自我验证。检测器和评估裁判应尽量解耦，并加入人工抽样复核。

### 性能与可扩展性

语义图和关系分析可能随 agent 数量、代码实体数量快速增长。应报告索引延迟、查询延迟、存储开销，以及在 2/4/8/16 个并行 agent 下的退化曲线。

## 15. 顶会级主张的最终形式

在证据充分前，只应提出以下可检验主张：

> 我们提出 ISCC，一种与 Git 兼容的任务—意图—语义实体变更表示及治理机制。通过把协调决策从 commit/merge 阶段前移到任务登记和变更形成阶段，ISCC 能够识别部分传统 Git 无法识别的语义风险，并在保持有效并行度的条件下降低重复工作和集成成本。

不能提前提出以下未经验证的强主张：

- “ISCC 能解决 AI 编程中的所有协作问题”；
- “传统 Git 已经不再适用”；
- “LLM 可以准确理解所有代码意图”；
- “自动合并可以完全替代人工审查”。

## 16. 下一阶段的最小可行研究任务

下一轮不应同时实现所有功能。建议按以下顺序推进：

1. 构造 30–50 个包含真实或可验证语义冲突的任务对，完成双人标注；
2. 实现只读的 ISCC 记录格式和离线关系检测器，不接管 Git 合并；
3. 与文件级 diff、调用图重叠和纯 LLM 任务相似度三个基线比较；
4. 先验证 RQ1/RQ2 的检测质量，再决定是否实现主动治理和自动集成；
5. 只有当检测质量和标注一致性达到预设门槛后，才进入多 agent 在线实验。

建议的进入门槛为：关键标签的双人标注一致性达到预先设定水平；语义冲突检测相对文件级基线取得正向效应且置信区间不跨越零；检测延迟不会使 agent 等待成本抵消协作收益。具体阈值应在试验性数据后确定，而不应事后挑选。

## 17. 基准数据格式（可复现协议）

每个实验场景应以一个不可变的 `Scenario` 目录发布，至少包含以下文件：

```text
scenario.json       # 项目版本、语言、任务组合、随机种子、agent 配置
tasks.jsonl         # 任务描述、验收条件、预期实体和依赖
baseline/           # 场景开始前的干净 Git commit
agent-traces/       # 每个 agent 的消息、工具调用、时间戳和输出
changes/            # 原始 patch、ISCC 元数据和实体映射
tests/              # 基线、单变更、合并后和后续修复的测试结果
labels.jsonl        # 冻结后的冲突、重复、归属和集成债务标签
README.md           # 重放命令、许可、已知限制和数据来源
```

`tasks.jsonl` 中必须把“自然语言要求”和“可判定验收条件”分开。每个 ISCC 记录必须能通过 `task_id`、`agent_id`、Git object id 和测试证据回溯到原始上下文。所有时间戳统一使用 UTC；模型名称、版本、系统提示、工具权限和温度参数必须记录，避免实验无法重放。

## 18. 检测任务与系统治理任务的区分

论文应将两个容易混淆的任务分开：

### 18.1 离线检测

输入已经产生的任务和变更，输出冲突/重复风险及证据。该任务评价 precision、recall、校准误差和延迟，不改变 agent 行为。

### 18.2 在线治理

系统在 agent 执行过程中提供提醒、范围协商、任务取消、变更冻结或集成排序。该任务评价最终协作结果和人类成本，但会受到系统反馈改变 agent 行为的影响。

先完成离线检测再进行在线治理，能够避免把“检测准确”与“干预有效”混为一个未经解释的黑箱结果。

## 19. 风险评分与决策规则

ISCC 不应输出没有证据的二元“允许/禁止”。建议输出风险向量：

\[
  r(c_i,c_j)=(r_s,r_d,r_c,r_p)
\]

分别表示语义干扰、任务重复、概念冲突和来源不完整的风险，并附带证据：重叠实体、违反的约束、相似验收条件、缺失的验证步骤等。

在线策略只使用预先声明的阈值：低风险允许并行并记录关系；中风险提示 agent 或请求确认作用域；高风险暂停自动集成，要求人工或上游 agent 决策。风险阈值必须在开发集上确定，在测试集上锁定，不能依据测试结果反向调参。

## 20. 消融实验矩阵

为了证明收益来自完整的变更模型，而非单一的 LLM 相似度，应至少包含：

| 配置 | 任务卡 | 语义实体 | 来源证明 | 生命周期 | 目的 |
|---|---:|---:|---:|---:|---|
| Git-only | 否 | 否 | 否 | 否 | 传统工作流基线 |
| Task-only | 是 | 否 | 否 | 否 | 测量任务登记收益 |
| Task+Entity | 是 | 是 | 否 | 否 | 测量语义作用域收益 |
| Task+Provenance | 是 | 否 | 是 | 是 | 测量可追溯性收益 |
| Full-ISCC | 是 | 是 | 是 | 是 | 完整系统 |

若 Full-ISCC 只在“语义实体关闭”时失效，才可以支持语义作用域是关键机制的结论；若所有配置效果相同，则应收缩技术主张。

## 21. 样本量与实验单位

实验单位应是“一个项目版本上的一组并行任务场景”，而不是单个文件或单次模型调用。每个项目版本至少运行多个随机种子；不同项目版本不得将相同任务副本当作独立样本。

在正式实验前进行小规模方差估计，再根据预期效应量、场景内相关性和多重比较数量确定样本量。报告样本量计算假设、排除规则和所有失败运行；不能只保留成功完成的 agent 轨迹。

## 22. 成功判据与停止规则

建议在实验前注册以下最低成功判据：

1. 关键标签（含 `LF`）达到预设的标注一致性；
2. 语义冲突检测相对 Git-only 基线的主要终点取得正向效应；
3. Full-ISCC 在控制有效并行度后仍降低集成延迟或人工解决时间；
4. **H6 单独成立**：在无 TC/BC/AC 的重复触碰子集上，治理层降低意图断裂程度；若该子集上无效应，必须撤回 `M_legibility` 与 `LF`，不得只在总体指标上报告
   “ACCD 下降”来掩盖这一失败；
5. 没有以显著增加误报、模型成本或 agent 等待时间为代价；
6. 在至少一个历史回放轨道和一个受控生成轨道上方向一致。

若检测效果成立但在线治理效果不成立，论文应诚实地定位为“变更风险分析系统”，而不是继续宣称完整的版本控制替代方案。若只有合成任务成立，应将结论限定为受控场景，并把生态有效性留作后续工作。

## 23. 研究路线的阶段门

### Gate A：问题可测量

完成标签本体、标注手册和试点数据；证明语义冲突与重复任务不是无法一致判断的主观概念。

### Gate B：检测可用

离线检测器在冻结测试集上相对文件级基线获得稳定收益，并报告错误案例、校准和延迟。

### Gate C：治理有效

在线反馈在不降低有效并行度的情况下改善集成质量或人类成本；所有 agent 轨迹完整记录。

### Gate D：顶会论文

完成跨项目复现、消融、用户研究、开放基准和局限性分析。只有通过 Gate D，才适合将贡献表述为通用的 AI 原生变更治理机制；否则应准确限定为某一检测组件或特定场景工具。

## 24. 统一理论构念：AI 变更协调债务

当前的语义冲突、重复实现、工作区污染、分支爆炸与**反复修改导致的意图流失**不应只作为五个平行痛点罗列。建议将它们统一为一个中介构念：**AI 变更协调债务**（AI Change Coordination Debt, ACCD）。

ACCD 指：由于 agent 产生的变更缺乏任务归属、意图、语义影响和生命周期信息——且**任务声明与变更之间的绑定只存在于会话历史中**——团队在后续理解、去重、验证、重构和集成阶段必须额外付出的可观测成本。

其核心因果链可以表示为：

```text
开发者并行开启的 agent 会话数（并发度）
        ↓
任务声明与变更的绑定随会话丢失 + 变更语义信息缺失（意图、实体、来源、状态）
        ↓
AI 变更协调债务（ACCD）
        ↓
冲突、重复、概念分歧、可理解性侵蚀、污染、分支碎片化
        ↓
集成延迟、返工、回归缺陷、维护与认知成本
```

五类现象与 ACCD 的对应关系为（**每一类现象必须恰好落进一个维度，不允许出现无处安放的现象**；完整维度集合见 §33）：

| 现象 | 可观测表现 | ACCD 的具体维度 | 对应标签 |
|---|---|---|---|
| 重复触碰导致意义流失 | 行为兼容但该处无法回溯到任何单一任务 | 可理解性侵蚀（legibility） | `LF` |
| 语义冲突 | 文本可合并但行为/架构不一致 | 影响范围与约束缺失（interference） | `TC`、`BC`、`AC` |
| 重复实现 | 多个会话完成重叠目标 | 任务身份与验收条件缺失（redundancy） | `RT`、`RI` |
| 概念分歧 | 同一规范概念出现多个名称或接口 | 任务身份与验收条件缺失（redundancy） | `CC` |
| 工作区污染 | 文件无法归属、半成品堆积 | 来源与生命周期缺失（provenance） | `UA` |
| 分支爆炸 | 短分支增多、合并失败 | 依赖和集成关系缺失（fragmentation） | 分支指标、`ID` |

这张表是 §24 与 §33 的**唯一对接口径**：任何新增标签都必须能在此表找到所属维度，任何新增维度都必须至少承接一个标签；否则该构念出现了新的覆盖缺口。

这个统一构念的作用是避免论文变成“功能列表”：系统不是分别解决五个问题，而是减少导致五类问题共同出现的信息缺失。

## 25. 因果模型与主要结果变量

建议把实验假设写成一个可检验的因果模型：

\[
Y = f(X, M, Z)
\]

其中：

- \(X\)：协作条件，包括 agent 并行度、任务相似度、实体重叠度和异步延迟；
- \(M\)：ACCD，中介变量，由协调信息缺失引起；
- \(Z\)：治理处理，即 Git-only、部分 ISCC 或 Full-ISCC；
- \(Y\)：最终协作结果。

主要结果变量应限定为一到两个，避免多重终点削弱论文叙事。建议将 **单位有效功能的集成成本** 作为主终点：

\[
  C_{integration}=
  \frac{T_{integration}+\lambda_1 T_{human}+\lambda_2 T_{rework}+\lambda_3 N_{regression}}
  {N_{validated\ features}}
\]

其中：

- \(T_{integration}\)：从首个 agent 完成到变更进入主线的时间；
- \(T_{human}\)：人工审查和冲突解决时间；
- \(T_{rework}\)：因重复或语义冲突产生的返工时间；
- \(N_{regression}\)：合并后回归缺陷数量；
- \(N_{validated\ features}\)：最终通过验证并保留的有效功能数量。

权重 \(\lambda\) 不应事后选择。可以先分别报告原始维度，再在预注册中声明一个主分析权重，或使用标准化后的无权综合指标作为敏感性分析。

## 26. 从“检测准确率”到“协作收益”的证据链

顶会论文不能用检测器 F1 直接推断系统改善了软件开发。需要建立分层证据链：

1. **表示层证据**：ISCC 能否正确抽取任务、实体、意图和来源；
2. **关系层证据**：ISCC 能否识别重复、重叠、依赖和矛盾关系；
3. **决策层证据**：这些关系是否改变了 agent 的任务选择、作用域或集成顺序；
4. **结果层证据**：决策变化是否降低 ACCD 和集成成本；
5. **人因层证据**：开发者是否更快、更准确地理解和处理变更。

每一层都要有独立指标。若关系识别准确但并未改变决策，论文应报告“分析能力”；若决策改变但最终结果没有改善，应报告治理策略失效，而不能把两者合并成正向结论。

## 27. 最小核心贡献的重新表述

经过收敛，最值得优先验证的不是“完整 AI Git”，而是以下单一贡献：

> **一种任务前置、意图作用域化的变更协调机制：在 agent 开始修改代码前登记可验证目标和预期语义实体，并在变更形成过程中维护其来源、关系和状态，以减少后续的 AI 变更协调债务。**

这一定义有三个好处：

- 把治理时机前移到代码修改之前，而不是只在 merge 时做补救；
- 把“意图”绑定到可验证实体和验收条件，降低空泛的自然语言解释风险；
- 把系统成功标准设为降低协调债务，而不是追求完全自动合并。

## 28. 论文叙事建议

一个适合顶会投稿的论文结构可以是：

1. **Introduction**：展示多会话 agent 开发中“文本无冲突但集成失败”以及“反复修改后无人能回溯其意义”的反例，提出 ACCD；
2. **Empirical Characterization**：用历史回放或受控任务证明五类现象共同存在；
3. **Model**：定义 ISCC、语义影响和变更关系；
4. **System**：实现任务登记、关系检测、生命周期和证据链；
5. **Evaluation**：分别评估表示、检测、在线治理和人类成本；
6. **Ablation and Failure Analysis**：证明收益来自哪些模块，展示误报和漏报；
7. **Discussion**：说明适用边界、隐私问题、模型漂移和人工责任；
8. **Conclusion**：只总结实验支持的有限主张。

论文开头应使用一个能说明“Git 文本一致性不等于软件协作一致性”的具体案例，而不是一开始罗列插件功能。

## 29. 顶会审稿风险清单

以下问题必须在正式投稿前主动回答：

- **新颖性风险**：ISCC 是否只是 issue、PR、代码图和 LLM 摘要的重新包装？必须明确哪个新抽象产生了此前没有的决策能力。
- **自动化风险**：意图和语义实体由模型抽取时，错误会不会制造新的协调债务？必须报告错误传播和人工修正成本。
- **基线风险**：若 Git-only 基线过弱，收益没有说服力。应加入最强的文件级、调用图级和人工协调基线。
- **并行性风险**：系统可能通过禁止重叠任务而获得低冲突。必须报告有效并行度、被阻塞时间和单位有效功能吞吐。
- **任务泄漏风险**：如果测试任务与提示模板或训练数据高度相似，结果可能高估。应隔离项目和任务来源，并报告重复检测。
- **评估循环风险**：同一 LLM 同时产生 ISCC、预测标签和裁决结果会形成自证。应尽可能使用独立模型、程序验证和人工抽样。
- **生态风险**：开发者是否愿意登记任务？必须测量登记负担，并支持从轻量自然语言输入逐步补全结构化字段。
  **注意**：在 §1.1 的主场景下（开发者本已在会话中声明任务），登记负担应当显著低于“多 agent 自治协作”场景；若实测登记负担仍然很高，说明实现方式与场景不匹配，而不是场景本身不成立。
- **`LF` 标签效度风险**：`LF` 是否只是把“文件被改过多次”换了个名字？必须在标注阶段证明两名标注者能独立、有证据地判定它，并在对照中证明它与 `TC`/`BC`/`AC` 不同时发生；若两者高度共现，说明它没有独立构念，应并入冲突类维度或撤销。

## 30. 当前版本的一页式研究摘要

**问题。** 开发者并行开启多个 agent 会话修改同一代码库时，代码变更具有异步、语义耦合和高频迭代特征；Git 的 commit/diff/branch 抽象无法记录任务意图、语义影响、来源和生命周期，而任务声明本身只存在于会话历史中，形成 AI 变更协调债务。其中一整类失败——同一处被反复修改后意义无法回溯——**不依赖任何冲突发生**，因此现有的冲突检测方法在定义上覆盖不到。

**方法。** 提出 ISCC，将任务目标、验收条件、预期实体、约束、实际 patch、agent 来源、验证证据和生命周期绑定为可治理变更对象，并定义重叠、重复、依赖、矛盾和替代关系。

**研究问题。** ISCC 能否比文件级 Git 协作更准确地发现语义冲突和重复任务？在线治理能否在保持有效并行度的情况下降低单位有效功能的集成成本？

**评价。** 使用历史回放与受控生成两条轨道，配合冻结标签、双人标注、消融实验、分层统计模型和开发者用户研究，分别测量检测质量、协调决策、集成结果和认知成本。

**可证伪结论。** 若 ISCC 不能在控制有效并行度、误报率、模型成本和登记负担后降低集成成本，则“意图作用域变更治理”这一核心主张不成立；论文应退回为问题测量或离线风险分析工作。

## 31. 下一轮的唯一优先事项

下一轮只做一个动作：建立 Gate A 的试点基准，而不是继续扩展系统功能。具体产物应包括：

1. 10–15 个项目版本或可公开复现的最小仓库；
2. 每个版本 3–5 组并行任务；
3. 覆盖五类失效的任务对和完整上下文，**其中必须包含至少一个 `LF` 正例**（行为兼容、测试全过、但同一实体被多次触碰且意义无法回溯）；
4. 标注手册、双人标注结果和一致性统计；
5. 一份包含正例、负例和模糊例的错误分析报告。

只有当 Gate A 证明 ACCD 的关键维度可被一致识别，才继续实现在线治理；否则应修改构念定义，而不是用更复杂的模型掩盖测量问题。

## 33. ACCD 的测量模型

ACCD 不应被直接压缩成一个由研究者事后调权的总分。建议将其定义为五维结果向量：

\[
  M=(M_{interference},M_{redundancy},M_{provenance},M_{fragmentation},M_{legibility})
\]

其中：

- \(M_{interference}\)：BC、AC、TC 以及后续回归缺陷；
- \(M_{redundancy}\)：RT、RI、**CC**，以及被删除/覆盖的重复变更（`CC` 归入本维度，因为“同一概念被实现成多个不一致的名字或接口”在机制上与重复实现同源：都是任务身份未被共享所导致的同一性丢失）；
- \(M_{provenance}\)：UA、无法解释的 patch 和缺失的验证证据；
- \(M_{fragmentation}\)：分支数量、分支生命周期、重放/再基化次数和集成等待时间；
- \(M_{legibility}\)：**LF**、同一实体的累积触碰次数，以及事后标注者能把保留形态回溯到有效任务的比例（可回溯率越低、累积触碰越多，该维越高）。

`M_legibility` 与前四维的关键区别是它**不依赖任何冲突发生**：两个行为完全兼容、测试全过的改动反复触碰同一处，仍会推高该维。因此它不能被 TC/BC/AC 的任何组合替代，也不能用“没有检测到冲突”当作该维为零的证据。

每一维先报告原始指标和标准化效应，不默认存在唯一的“协调债务分数”。综合指标只能作为预注册的敏感性分析，并且必须展示不同权重下结论是否稳定。这样可以避免把不可比的失败类型通过任意权重掩盖。

**覆盖完整性约束**：§24 的现象—维度对照表与本向量必须双向覆盖——每个标签至少属于一个维度（`TC/BC/AC`→interference，`RT/RI/CC`→redundancy，`UA`→provenance，`LF`→legibility，`ID` 与分支指标→fragmentation/结果层），每个维度至少承接一个标签。

建议将主结果限定为两个预先指定的终点：

1. **集成可靠性**：在满足任务验收条件的前提下成功进入主线的比例；
2. **单位有效功能的协调成本**：前文定义的 \(C_{integration}\)。

其余指标作为机制和副作用指标，而不是任意挑选的“显著结果”。

## 34. 因果估计对象

在线治理实验应把处理定义为完整的工作流，而不是某一个模型调用：

\[
  Z\in\{0,1\},\quad Z=0:\text{Git-only},\quad Z=1:\text{Full-ISCC}
\]

对每个场景 \(s\) 定义潜在结果 \(Y_s(0),Y_s(1)\)。主要估计对象为：

\[
  \tau=E[Y_s(1)-Y_s(0)]
\]

其中 \(Y\) 可以是集成可靠性或负的单位协调成本。报告 \(\tau\) 的置信区间，而不是把同一场景的两个运行结果当作彼此独立。

并行性约束应显式进入分析：

\[
  \tau_{parallel}=E[Y_s(1)-Y_s(0)\mid P_s(1)\geq P_s(0)-\epsilon]
\]

其中 \(P_s\) 是有效并行度，\(\epsilon\) 是预先声明的可接受下降幅度。若 Full-ISCC 通过大量阻塞 agent 获得低冲突，不能将该结果解释为真正的协作收益。

## 35. 处理分配与配对设计

对于同一 scenario，Git-only 与 Full-ISCC 应使用相同的基线 commit、任务集合、模型配置和随机种子；但为避免运行顺序影响，处理顺序应随机化。历史回放采用固定变更轨迹，在线实验采用配对随机种子。

若一个 agent 的输出会改变后续 agent 的输入，不能把每个 agent 当成独立实验单位。分析单位应提升为整个 scenario，并把项目、任务集合和随机种子作为层级结构。

## 36. 机制验证而非相关性叙事

为了支持“信息缺失导致 ACCD，再由 ISCC 缓解”的机制解释，至少要验证以下链条：

1. Git-only 条件下，任务/实体重叠与 ACCD 指标相关；
2. ISCC 确实改变了任务取消、作用域调整或集成顺序等中间决策；
3. 中间决策的变化与最终集成成本相关；
4. 在控制项目、任务难度和并行度后，处理效应仍存在。

如果只观察到 Full-ISCC 与低成本结果相关，但没有记录中间决策，就只能声称“工作流比较结果”，不能声称已经验证协调机制。

## 37. 负控与反事实检查

实验应加入至少一种负控：

- 任务实体完全不重叠、验收条件独立的场景；
- 只改变提交信息但不改变代码的场景；
- 只增加来源字段但关闭所有风险提示的场景。

在负控场景中，Full-ISCC 不应显著增加阻塞、延迟或成本。若连完全独立任务也被频繁阻塞，说明风险检测存在系统性过度干预。

同时报告反事实检查：对检测器标记为高风险的样本，人工移除其中一个变更或交换集成顺序后，风险后果是否消失或改变。该检查有助于区分真正的因果干扰与仅仅相关的文件重叠。

## 38. 版本化的研究主张

研究主张应随证据阶段升级，而不是一开始就固定为最强版本：

| 阶段 | 可以提出的主张 |
|---|---|
| 合成校准 | 标签和数据格式可被机器检查，场景能覆盖预设失效类型 |
| Gate A | 关键失效维度具有可操作定义和可接受的人工一致性 |
| Gate B | ISCC 在冻结数据上改善风险检测质量 |
| Gate C | 在线治理在控制并行度后降低协调成本 |
| Gate D | 该效果跨项目、跨任务类型和跨随机种子具有稳定性 |

如果证据只达到 Gate B，摘要和标题都不能使用“提高多 agent 软件开发效率”等 Gate C/D 级表述。

## 40. 研究定位修正：Git 之上的协调层

“Git 跟不上 AI”是有启发性的动机表达，但不是适合直接写进论文的技术命题。Git 仍然能够保存对象、记录历史、比较状态和执行三方合并；当前失配发生在 Git 之上的任务协调、意图对齐、变更归属和集成治理层。详细决策依据见 [研究定位决策记录.md](研究定位决策记录.md)。

需要同时说清这次修正**放弃了什么**：改判之后，本文不再把“Git 本身失效”当作研究对象或结论，因此**论文不会去检验该表述本身**。它只检验“在 Git 之上增加任务中心协调层是否改善协同结果”。若未来需要支持“Git 抽象本身不足”这一更强命题，必须另设实验（例如测量任务↔变更绑定的丢失率如何随会话并发度增长），不能从现有设计推导出来。

因此，后续论文和原型统一采用以下定位：

> **面向多会话 agent 开发的任务中心代码变更协调层（AI-native change coordination plane on top of Git）。**

ISCC 是该协调层中的变更表示，不是替代 Git 的全新版本数据库。该修正避免把“仍然有用的底层版本存储”与“缺少任务和意图一等对象的协同工作流”混为一谈，也把实验处理变量明确为协调层是否存在，而不是 Git 是否存在。

## 42. 真实历史初筛的第一条负控证据

已从公开 Flask GitHub API 成功提取 2 个已合并 PR 的元数据和 patch，并构造 1 个初筛候选对。候选对仅共享 `tests/test_basic.py`，且 PR 生命周期不重叠、生产代码实体不重叠，已被人工初审排除。详细证据见 `03_基准与标注/benchmark/real-history/flask/adjudication.md`。

该结果不是 ACCD 发生率，也不是语义冲突样本；它是一个**筛选误报负控**，证明文件路径交集不能直接作为语义冲突或重复任务标签。GitHub 匿名 API 在分页扩展时触发 403 rate limit，提取日志见 `03_基准与标注/benchmark/real-history/flask/retrieval_log.md`；后续采集需等待配额重置或使用获授权的只读访问方式。

本地 Git 提交图的扩展筛选显示：最近 120 个 merge commit 中有 80 个带 PR-like 标识的 merge row，但路径或时间规则会产生 805 个宽松候选；收紧到分支生命周期时间重叠后只剩 7 对，进一步要求共享生产路径后只剩 2 对。该结果强化了候选池分层和负控报告的必要性，也说明真实历史回放不能把“共享文件”直接解释为“agent 协作失败”。

对这 7 个时间重叠候选的初审见 `03_基准与标注/benchmark/real-history/flask/git-history/strict_candidate_adjudication.md`。其中 2 个共享生产路径的候选（PR 5812/5808、PR 5898/5808）在 patch 级别表现为不同方法或不同任务目标，当前作为筛选负控保留，而不是语义冲突真值。该结果进一步支持：路径重叠、时间重叠和语义协作失败必须在数据集中分层表示。

## 43. Git merge-tree 重放的负结果

在 Flask 本地提交图的 80 个 PR-like merge row 上，三方合并重放均得到 `auto_clean_same_tree`：自动合并树与实际提交树一致，且没有检测到文本冲突行。该结果不证明不存在语义冲突；它证明的是 Git 的 merge-tree 结果不足以作为 ACCD 的观测变量。后续真实正例必须增加任务验收条件、测试失败、后续修复/回滚或维护者讨论等证据。
