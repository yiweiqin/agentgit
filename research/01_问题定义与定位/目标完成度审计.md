# 目标完成度审计：AI 原生变更协调研究

## 审计日期

2026-09-14

## 审计对象

目标：将“用户以多个 agent 会话并行修改同一代码库，造成代码冲突、重复实现、工作区污染和分支合并困难”的观察，迭代为符合顶级软件工程/人机协作会议标准的学术化问题定义、研究假设、研究目标和可验证评价框架。

> **场景锚点（2026-09-14 修正）**：目标陈述中的"多 agent 并行"已收敛为**单开发者 × 多 agent 会话**（主文档 §1.1），
> 以忠实于原始观察并避免与"多 agent 自治协作"混淆。该修正同时新增了第 9 条完成条件（见 §完成条件）。

## 判定结论

当前状态：**proposal-ready，尚未 paper-ready，也尚未完成实证研究。**

已经具备：问题模型、核心构念、技术边界、研究假设、实验协议、标注手册、合成校准集、基准验证器、相关工作初筛和部分全文证据。

尚未具备：真实多 agent 会话数据集、人工标注一致性结果、在线治理原型、跨项目效果、开发者用户研究和统计效应证据。因此不能把目标标记为 complete。

> **2026-09-14 构念审计发现的三个覆盖缺口（已在文档层修复，尚未在数据层修复）**

> 1. **原始痛点的第一条有一半没有标签。** 原始观察是“同一处代码被修改多次后无人知道其意义且难以维护”。
>    其中“意义无法回溯”这一半在**行为兼容、无任何冲突**时同样发生，而原有 8 类标签只覆盖**升级为冲突**的情形，
>    在此情形下会全部判 `no`。修复：新增 `LF` 标签、ACCD 新增 `M_legibility` 维度、新增 H6。
> 2. **`CC` 在测量模型里无归属。** `CC` 在 `§11.1`、`§24`、`§33` 三处缺失，而标签本体一直有它。
>    修复：明确归入 `M_redundancy`（与 `RT`/`RI` 同源：任务身份未共享导致的同一性丢失），并加入覆盖完整性约束。
> 3. **原始痛点第三、四条在当前数据里测不到，且是被采样方式排除的。**
>    `UA`（工作区污染）因 `agent_context_summary` 不可得而不可判定；分支爆炸的样本（未合并的分支）在定义上不出现于 merge 历史中，
>    因此被候选生成方式系统性排除。这两条目前**没有任何正例来源**，必须在扩充候选池时显式处理。
>
> 上述三项的登记见 `03_基准与标注/benchmark/real-history/flask/git-history/annotation/adjudication_log.md` 的 D3。
> **修复性质的区分很重要**：缺口 1 与 2 是文档层缺口（已修）；缺口 3 与 `LF` 的可判定性问题是**数据层缺口**（未修），

## 主张强度审计

### 当前可以声称

- 开发者以多个 agent 会话并行修改同一代码库时，传统 commit/diff/branch 抽象之外存在协调信息缺失问题；
- ACCD 和 ISCC 是一个具有明确变量、标签和实验协议的研究框架；
- 当前合成试点覆盖预设失效类型，并通过了结构验证；
- 已核对的相关工作表明，语义冲突检测、agent 交互和多 agent 通信已有先行研究，因此 ISCC 的新颖性必须限定在统一的任务中心变更协调层；
- **可以声称（理论层）**：“反复修改同一处导致语义归属稀释”这一失败类别，在定义上落在既有语义冲突检测的覆盖面之外——这是任务定义的差异，不是检测精度差异。

### 当前不能声称

- ISCC 已经降低了开发成本或冲突率；
- Git 已经不适用于 AI 软件开发；
- ACCD 在真实项目中的发生率已经被测量；
- ISCC 比 ConflictLens、程序分析或现有 agent 框架更有效；
- 该框架已经达到顶会论文的实证标准；
- **`LF` 已被校准或已可判定**——当前 7 个候选上 `LF` 全部不可判定（无任何候选的两个 PR 触碰同一符号），
  既没有合成校准场景，也没有真实正例，因此 H6 目前**完全没有证据**；
- **工作区污染与分支爆炸已被测量**——两者在现有数据中没有任何正例来源。

## 完成条件

只有在以下证据全部存在时，才可把目标标记为 complete：

1. 真实或可公开重放的**多会话 agent** scenario 数据集；
2. 双人独立标注、第三方裁决和各标签一致性统计；
3. 可运行的 ISCC 离线检测器和明确的强基线；
4. 冻结测试集上的检测结果、误报/漏报分析和延迟；
5. 在线治理的配对实验，且控制有效并行度；
6. 集成可靠性、单位有效功能成本和人类成本的效应量及置信区间；
7. 至少跨项目或跨任务类型的复现；
8. 完整披露失败运行、数据许可、模型版本、提示词和已知限制；
9. **主场景保真度证据（新增）**：至少一个直接来自「单开发者 × 多 agent 会话」观测的 scenario
   （而非人类并行 PR 代理），否则所有结论必须始终限定为"并行变更流"层级；
10. **`LF`/H6 的最小证据链（新增）**：至少一个符号级反复触碰的正例、
    一次合成校准（`gateA-pilot` 补 `LF` 场景）和一次两名标注者对 `LF` 的独立判定，
    且 `LF` 与 `TC`/`BC`/`AC` 的共现矩阵支持其独立性（否则按 H6 撤销该标签）。

## 下一步最有信息价值的行动

不是继续增加理论段落，而是完成一个真实 scenario 的端到端切片：从公开仓库基线、任务与并行变更提取开始，到双人标注、标签冻结、Git-only/ISCC 离线检测和错误分析结束。这个切片将直接检验数据可获得性、标签可判定性和检测器输入是否足够。

Flask 试点已经完成提交图、候选筛选、patch 固定和 merge-tree 重放，但 80 个 PR-like merge row 均无自动树与实际树差异。因此当前真实生态证据仍属于“筛选负控和数据方法验证”，尚未获得 ACCD 正例或人工一致性统计。

目前又完成了 7 个时间重叠候选的空白标注队列和 10 个公开 PR patch 的 SHA-256 固定；这些资产足以启动人工标注，但不能替代两名标注者的独立判断。

当前候选集在两条线上同时失效：全部为负控（D2）且无法判定 `LF`（D3）。两者都由同一次候选扩充解决，因此不应分两步做：

1. 扩充候选池，纳入条件改为**双轨**——既要有历史正例（后继修复/回滚证据），
