## 0. 先讲清楚：这个框架推翻了哪三处既有决策

用户原话：

> 多开发者在使用多个 agent 开发软件时，AI 改动速度过快和有限的上下文导致工作区混乱，无法像前 AI 时代通过 git 进行精准的版本控制，我们希望通过制作一个可以代行 Git 功能的 agent，用 AI 治理 AI 带来的混乱。

这与本仓库此前三次决策冲突。逐条说明**代价**，然后给出**能保住原意但不被一击反驳**的重构：

| # | 被推翻的决策 | 原决策出处 | 原决策的理由 | 本框架的代价 | 处理方式 |
|---|---|---|---|---|---|
| 1 | "Git 仍能精准版本控制，缺的是任务层" | `研究定位决策记录.md` §1 | "Git 跟不上 AI" 易被一句话反驳 | 重新背上被 desk-reject 的语句 | **必须改写**：问题不在"精度"而在**归属吞吐**——见 §2.3 |
| 2 | 场景收敛为"单开发者 × 多会话" | 主文档 §1.1 | 忠于"一人开多个窗口"的原始观察 | 数据获取难度**再升一级**（需多开发者 × 多 agent） | **接受**：多开发者更普适、更可发表；但写进 §6 的门槛 |
| 3 | "Git 之上的协调层"，不替代 Git | `研究定位决策记录.md` §2 | 避免"重写 Git"这种不可防守的主张 | 需要重新说清"代行"到底代行什么 | **重解释**：代行的是 Git 工作流**指派给人**的调和职责，Git 仍是存储底座——见 §4 |

**我的建议**：第 2、3 条照用户的方向走（它们可以被严谨化），**只有第 1 条必须改写**。理由见 §2.3，一句话是：**说"Git 不够精准"会被反驳，说"Git 的调和吞吐跟不上 agent 的变更速率"既忠于原意又无法被反驳。**

## 1. 这个框架为什么比上一版强（诚实的比较）

我不是在迁就，这版在**理论机制**上确实优于上一版：

| | 上一版（ACCD / 意图稀释） | 本框架 |
|---|---|---|
| 根因 | 变更**缺少**任务/意图/来源元数据 | agent **上下文有界** + 变更**速率**超过调和能力 |
| 根因的性质 | 描述性（"缺字段"） | **因果性 + 技术必然性**（上下文窗口是硬约束，不是选择） |
| 可证伪的核心量 | 元数据完备度 | **速率比 \(\lambda/R\)** 与 **失配** |
| 为什么是现在 | 定性 | **可给出临界点**：\(\lambda\) 跃升而 \(R\) 不变 |
| 设计立场 | 加一层协调平面 | **用 AI 治理 AI**（AI 抬高 \(R\)） |
| 制品形态 | 协调层 | **一个代行版本控制职责的 agent**（可演示、有主体） |

最关键的一条：**"有限的上下文"是一个真正的机制，而"缺少元数据"只是一个症状。** 上几版的 `LF`（意图稀释）与 `M_legibility` 不但不浪费，反而被本框架**解释**了——见 §2.4。

## 2. 痛点（学术表达）

### 2.1 中文

> 当多个开发者各自驱动多个具备**有界上下文**的 agent 并行修改同一代码库时，变更到达速率 \(\lambda\) 相较前 AI 时代跃升若干数量级，而系统的调和能力 \(R\)——即为每个变更建立归属、验证其后果、并把它并入可解释的仓库状态的能力——仍受人类审查与 Git 提交粒度的约束。一旦 \(\lambda\) 持续超过 \(R\)，未被调和的变更开始累积，仓库状态进入**局部自洽但全局不可解释**的形态：每一个 agent 在其上下文窗口内都是正确的，但没有任何参与者（人或 agent）能重建工作区为何处于当前状态。此失效的根源不是 Git 缺少精度，而是**版本控制的调和吞吐与 agent 的变更速率之间出现了结构性失配**。

### 2.2 English

> When multiple developers each drive several agents with **bounded context** to modify a shared repository in parallel, the change arrival rate \(\lambda\) exceeds its pre-AI baseline by orders of magnitude, while the system's reconciliation capacity \(R\)—the rate at which a change can be attributed, validated, and absorbed into an explainable repository state—remains bounded by human review and commit granularity. Once \(\lambda\) persistently exceeds \(R\), unreconciled changes accumulate and the repository enters a state that is **locally coherent but globally inexplicable**: every agent is correct within its own context window, yet no participant can reconstruct why the workspace is in its current state. The root cause is not a lack of precision in Git, but a **structural mismatch between the throughput of version control and the velocity of agent-driven change**.

### 2.3 为什么必须把"不够精准"改掉（关键）

用户原话是"无法像前 AI 时代通过 git 进行精准的版本控制"。这句话有三个可被反驳的读法，而它们**都错**：

| 读法 | 为什么会被反驳 |
|---|---|
| Git 的存储/分支/合并算法坏了 | 没坏。三方合并、内容寻址、历史图至今是工程上最好的解 |
| Git 不能追踪细粒度变更 | 能。`git diff` 的精度是行级的，比"任务级"更细 |
| Git 无法表达 AI 的变更 | **这个反驳不了**——但严格说，Git 从来也不是为**任务语义**设计的，这不是"AI 带来的退化" |

**换成"吞吐失配"后，三处反驳全部失效**，因为新命题完全是量化的、可测的、并且**不要求 Git 有任何缺陷**：

> Git 的设计前提是 \(\lambda \approx R\)：变更由人写出、由人审阅、以人可解释的粒度提交。当 \(\lambda\) 跃升而 \(R\) 不变时，**不是 Git 坏了，是它的设计前提不再成立**。

这个改写同时**保住了用户的原始直觉**（"AI 来了之后版本控制跟不上了"），只是把"跟不上的东西"从**精度**换成了**吞吐**——而后者是可测量、可证伪、可写进论文的。

### 2.4 本框架如何解释前几版的发现（不是丢弃，是收编）

- **意图稀释 / `LF`**：不再是一个独立现象，而是 \(\lambda>R\) 的**后果**。上下文有界的 session 各自局部最优 → 同一实体的多次触碰无人持有全局解释 → 稀释。**机制到位了，构念从描述变成因果。**
- **绑定存活率 \(B\)**：成为 \(R\) 的一个可测分量（归属吞吐）。
- **任务重复 / 概念分歧**：成为"无全局视图"的直接产物——两个 session 在各自上下文里都合理地发明了同一概念的两种命名。
- **工作区混乱**：成为 backlog \(B(t)\) 的可观测面。
- **分支爆炸**：成为开发者对 \(\lambda>R\) 的**本能抗击**（用隔离替代调和），而本仓库已实测其在 Flask 上失败（80 个 merge row 全部自动树一致）。

**收编的结果**：原来五个平行痛点 + 一个新增标签，现在统一为**一个失配 + 一个机制 + 一组后果**。这是一次真正的理论简化。

## 3. 形式化：把工作区建模为一个调和队列

### 3.1 三个量

| 符号 | 含义 | 单位 | 可测性 |
|---|---|---|---|
| \(\lambda\) | 变更到达速率（每开发者每 agent 的变更/时间，或每仓库的变更/时间） | changes·h⁻¹ | 可从 git 历史 + agent 日志直接测 |
| \(R\) | **调和能力**：单位时间内可被完成"归属 + 验证 + 并入可解释状态"的变更数 | changes·h⁻¹ | 可从审查时长、CI 时长、返工率反推 |
| \(B(t)\) | 未调和积压：\(\displaystyle B(t)=\int_0^t \max\big(0,\ \lambda(\tau)-R(\tau)\big)\,d\tau\) | changes | 可由 \(\lambda,R\) 积分或直接计数 |

### 3.2 核心命题

> **命题 1（失配）.** 当 \(\lambda>R\) 持续存在时 \(B(t)\) **无界增长**；当 \(\lambda\le R\) 时 \(B(t)\) 有界。
> **命题 2（工作区不可解释性）.** 仓库状态的不可解释程度是 \(B(t)\) 的单调非减函数。

**这不是重言式**：命题 2 是一个可被否证的**经验断言**——它可能不成立（例如积压被很好的工具在事后填补，从而不产生不可解释性）。这正是要做的实验。

### 3.3 前 AI 时代为什么没事

前 AI 时代 \(\lambda\) 由人类打字速度与思考速度上界约束（量级：\(10^0\) changes·h⁻¹/人），而 \(R\) 的量级相当（人审一段 diff 的速率）。**\(\lambda\approx R\) 是 Git 工作流的隐含设计前提。** agent 把 \(\lambda\) 推到 \(10^2\)–\(10^3\)，而 \(R\) 没有量级变化（人还是那个人）。

> 因此本文的主张可以精确表述为：**agent 驱动开发的失效不是 Git 的功能缺陷，而是它的量级前提被打破。**

### 3.4 由此得到的可证伪预测

| 编号 | 预测 | 若为假则 |
|---|---|---|
| P1 | 存在临界比 \(\lambda/R\approx 1\)，跨过后积压增长率显著上升 | 失配模型不成立，撤回 |
| P2 | 不可解释度对 \(B(t)\) 单调（命题 2） | 积压是可恢复的，治理需求被夸大 |
| P3 | **在固定 \(\lambda\) 下**，抬高 \(R\) 降低不可解释度（这是"用 AI 治理 AI"的核验） | AI 治理无效，本方案失败 |
| P4 | 在固定 \(R\) 下，降低 \(\lambda\)（阻塞、串行化）也能降低不可解释度 | —（这是**平凡解**，见 §3.5） |
| P5 | 控制 \(\lambda/R\) 后，agent 驱动的变更与人类变更产生同等不可解释度 | 失效来自 agent 的**质**（上下文有界、无全局视图），而非**量**（速率）；构念需重写 |

**P5 是全部设计中最重要的一个**——它区分"量的问题"与"质的问题"。若 P5 为真，本文只是"更多变更更难管"的量化版，贡献偏薄；若 P5 为**假**（即 agent 变更在同等 \(\lambda/R\) 下更糟），则**上下文有界性被证明是独立病因**，本文的理论贡献立刻变厚。**论文必须把 P5 作为核心实验来做，而不是附录。**

### 3.5 必须封死的平凡解：P4

降低 \(\lambda\) 是最廉价的"解决"方式——**禁止并行就行了**。这是本方案最大的方法学风险，且它**已经被本仓库既有设计预先处理**：主文档 §34 的 \(\tau_{parallel}\) 与 H5（非退化并行性）正是为此写的。

必须写进论文的约束：

\[
  \tau=E\big[Y(1)-Y(0)\ \big|\ P(1)\ge P(0)-\epsilon\big]
\]

其中 \(P\) 是有效并行度。**任何以降低 \(\lambda\) 换取的改善都不算治理收益。** 若治理 agent 的收益完全来自阻塞，论文必须诚实降级为"限流工具"，而不是"AI 治理"。

## 4. 「代行 Git 功能的 agent」到底代行什么

这是最需要说清的一处，否则会被读成"重写 Git"。

**Git 的工作流把人指派为若干职责的承担者**。本研究的系统把这**部分职责**移交给一个治理 agent：

| Git 工作流中人的职责 | 治理 agent 是否代行 | 说明 |
|---|---|---|
| 决定何时提交、以什么粒度 | ✅ | 按任务边界而非时间边界切分变更 |
| 建立归属（谁、为哪个任务改的） | ✅ | 移交后 \(R\) 的主要提升来源 |
| 发现重复任务/概念分歧 | ✅ | 需要一个全局视图——**这正是单 session 做不到的** |
| 判断两处改动是否语义干扰 | ✅ | 复用既有语义冲突检测作为组件 |
| 决定合并顺序 | ✅ | 按依赖直性与风险排序 |
| **提供不可变的对象存储与历史图** | ❌ | **仍由 Git 承担** |
| **执行三方合并算法** | ❌ | 仍由 Git 承担 |
| **最终审美/架构判断** | ❌ | 仍由人承担 |

**定位表述**：

> **一个以 Git 为存储底座、代行其工作流中人类调和职责的治理 agent。** 它不重写 Git，它接管 Git 工作流**假定由人来完成**的那部分吞吐。

英文：**A governance agent that takes over the reconciliation duties Git's workflow assigns to humans, on top of Git as storage.**

这个定位同时满足三件事：保住用户"代行 Git"的原意；避开"替代 Git"的不可防守主张；给出一个**可演示的主体**（一个 agent），而不是一个抽象平面——后者的可传播性差得多。

### 4.1 实现形态：宿主 hook 插件（2026-09-15 定）

不构建独立 agent 系统，实现为**宿主 hook 插件**（Cursor `hooks.json` / Codex `.codex-plugin`）。

**这个选择是方法上必要的，不只是更便宜**：\(B(t)\) 在原理上不可由 Git 历史观测（§10.3），要研究失配就需要一个能观测 \(\lambda_{\text{produced}}\) 的通道——而**治理 agent 是唯一天然持有该观测位的工件**，因为它必须在变更发生时当场干预。

> **治理与观测是同一个工件的两个面。** 这补上了 §9 第 6 项这个唯一硬瓶颈，并同时回应 R2（"没有数据"）与 R3（"不可测"）。

**两模式分离（效度要求）**：`instrument`（只读测量基线）与 `governor`（干预，作为 treatment）。若同时开启，则"有记录期"与"无记录期"不可比，H4/H5 的效应量无法解释。v0.1 只实现 instrument。

**R4「用 AI 治理 AI 是循环论证」的实现级回答**：治理不靠更大的上下文，靠**外置持久账本**。上下文有界限制的是同时推理的内容量，不限制持久化的关系表。hook 运行在某个 session 内，**但其状态不在该 session 的上下文里**——这正是它不受同一窗口约束的原因。

**关键发现**：`preCompact` 事件是"上下文有界"的**具体、带时间戳的观测点**。挂上它之后，H3 从主张变成可做的比较：

\[
  \text{不可解释度}/\text{返工} \sim \text{距上次上下文丢失的写入数}
\]

**我判断这是本框架里最可能出论文的一张图。**

**发现的真实缺口**：`context_compacted` **不在 ISCC v0.1 的事件枚举里**——即 ISCC v0.1 无法记录它自己框架的根因。需要 `iscc-0.2` 把"产生变更时的上下文状态"纳入 provenance。

详细设计与实现状态见 [`04_协调插件/README.md`](../04_协调插件/README.md)。

## 5. 研究问题与假设

| RQ | 问题 | 对应假设 |
|---|---|---|
| RQ1 | 速率–调和失配是否可测？是否存在临界比？ | H1 |
| RQ2 | 积压是否解释工作区不可解释性？ | H2 |
| RQ3 | agent 变更是"量"的问题还是"质"的问题？ | H3（= P5，核心） |
| RQ4 | 治理 agent 能否在**不降低并行度**的前提下提高 \(R\)？ | H4 + H5 |

- **H1（失配存在性）**：\(\lambda/R\) 越过临界值后，积压增长率显著上升。
- **H2（失配→混乱）**：不可解释度随累积积压单调上升。
- **H3（质而非量）**：控制 \(\lambda/R\) 后，agent 驱动变更的不可解释度**显著高于**人类变更——即**上下文有界性是独立病因**。
- **H4（AI 治理有效）**：治理 agent 在固定 \(\lambda\) 下显著抬高有效 \(R\)，降低积压与不可解释度。
- **H5（非退化并行性）**：H4 的收益在控制有效并行度 \(P\) 后仍然存在，不是靠阻塞换来的。

> **H3 是本文的理论赌注，H5 是本文的方法学防线。** 两者缺一不可：没有 H3 则贡献薄（只是"更快更难管"）；没有 H5 则收益可被"你只是限流了"一句话消解。

## 6. 指标

| 构念 | 操作化 | 备注 |
|---|---|---|
| \(\lambda\) | 单位时间进入仓库的变更数（按 task 边界归并，避免被提交习惯污染） | 必须报告**按任务归一**后的值 |
| \(R\) | 单位时间被完成归属+验证的变更数 | 从审查时长、CI 时延、返工率反推；须给出估算方法 |
| \(B(t)\) | 未调和积压 | 直接计数 + 积分校验 |
| **不可解释度** | 独立评审者能否重建工作区当前状态的成因（逐实体） | **复用既有标注链路**（标注包+校验器+一致性脚本） |
| 有效并行度 \(P\) | 并发活跃任务数 × 并行时长占比 | **H5 的分母，必须与主结果同时报告** |
| 代价 | 返工、回滚、集成延迟、单位有效功能成本 | 已有 `repair_or_revert_history` 路径级证据可用 |

**必须控制的混淆**：任务规模、语言/生态、仓库年龄、测试覆盖率、评审者熟悉度、以及 **commit message 质量**（旧版 K4 的生死线仍然有效）。

## 7. Kill criteria

| 编号 | 触发条件 | 后果 |
|---|---|---|
| K1 | 不存在临界比（P1 假） | 失配模型不成立，撤回 |
| K2 | 不可解释度与积压无关（P2 假） | 治理需求被夸大，降级为量化描述 |
| K3 | **P5 为真**（agent 变更只是"量"的问题） | **理论贡献降到"更快更难管"**，应改投工具轨 |
| K4 | H4 收益完全来自阻塞（H5 假） | 降级为限流工具，不得称"AI 治理" |
| K5 | 不可解释度的双人一致性不达标 | 换仪器或弃用该指标 |
| K6 | 多开发者多 agent 数据无法获得 | 只能用代理，全部结论限定为"并行变更流"层级 |

> **K3 与 K4 是本方案的两条命门**：前者决定理论分量，后者决定是否被"你只是限流"一句话击穿。必须在预注册里写明。

## 8. 评委会预演（本框架下）

### R1｜"这不就是 Little's Law？排队论里没有新东西"

> **一击.** "You modeled a queue and stated that when arrival rate exceeds service rate, backlog grows. That is textbook. Where is the scientific contribution?"

**这是本框架下最危险的一击**，比上一版的"定义平凡"更尖锐，因为**它大体正确**。

**答辩（必须写进正文，不能留给 rebuttal）**：
1. 我们**明确承认**队列模型是借用的工具，并把它当**引理而非定理**；
2. 贡献在于**识别出 \(R\) 是被忽略的变量**。此前把"AI 让开发变快"当收益；我们指出**\(\lambda\) 单独上升是负债**，除非 \(R\) 同步上升——这个"\(R\) 是瓶颈"的定位是本领域尚未采取的视角；
3. 贡献在于 **H3（质 vs 量）**：队列模型无法区分二者，而 H3 是经验问题；
4. 贡献在于**可操作的干预**：抬高 \(R\) 的具体机制（治理 agent）与其非退化性约束。

**现状**：⚠ 需 2、3 两条的证据。第 2 条可用**已有历史数据**做（估算 \(\lambda\) 的时间序列、看 \(R\) 是否跟随），第 3 条需新数据。

### R2｜"这是 proposal 不是 paper"

与上一版相同，且**更严重**：现在需要的数据是**多开发者 × 多 agent**，比单人多会话更难获得。

**现状**：✗ 唯一硬瓶颈，且比上一版更贵。**这是选择多开发者口径必须付的代价。**

### R3｜"\(\lambda\) 和 \(R\) 都不可测，模型不可证伪"

> **一击.** "You define \(R\) as 'the rate at which changes can be attributed, validated, and absorbed'. That is three things, none of them measured. Your model cannot be falsified because nothing in it is observable."

**最需要正面处理的一击。** 答辩：给出**可执行的估算规程**（见 §6），并报告每个量的**测量误差**与敏感性分析。若 \(R\) 无法被稳定估算，就必须承认模型只有**定性**价值，并据此收缩主张。

**现状**：⚠ 估算规程可写，但**没有实测**。这是可立即开工的补强。

### R4｜"用 AI 治理 AI 是循环论证"

> **一击.** "Your governor is an LLM with the same bounded context that caused the problem. How can a bounded-context system maintain global coherence?"

**这是针对本设计立场最本质的一击，也最有意思。**

**答辩（这是本文可以得分的正面论点）**：治理 agent 不需要持有全部内容，它需要持有**索引与不变量**——即"每个变更归属哪个任务、它与哪些变更共享实体、哪些实体缺乏归属"的**结构化账本**。它在计算上不受"读完全部代码"的限制，因为归属关系是**可增量维护的**，而不是每次重新推导。**上下文有界性限制的是同时推理的内容量，不限制持久化的关系表。** 这正是"用 AI 治理 AI"在原理上可行的理由——也是本设计相对"再开一个更大的 agent"的关键区别。

**现状**：⚠ 论证强，但需 **实现证据**（demo 级即可初步支撑）。

### R5｜"多开发者场景下，问题会不会只是沟通不良？"

答辩：沟通不良在异步分布式团队里早已存在且被研究；本文的失配模型给出**可测的区分**（\(\lambda/R\) 与归属吞吐），并能预测**沟通良好时仍会失败**。

**现状**：⚠ 需设计证明沟通变量被控制。

### AC｜元评审预测

> "The velocity–reconciliation framing is a genuinely interesting reframing, and the reversal from precision to throughput is well-argued. But the paper rests on two unmeasured quantities and has no data. Major revision at best; likely reject at a top venue until the measurement instrument exists."

**预测结局**：**今天投出去 = 拒稿**，且比上一版**更依赖 R1/R3 的答复质量**。

**但有一个重要差别**：上一版的卖点是"定义域缺口"（概念性，审稿人认可与否各半）；本版的卖点是"**\(\lambda\) 跃升而 \(R\) 不变，因此 \(R\) 是瓶颈**"——这是一个**更容易被直觉接受、也更容易用现有数据先做出初步证据**的主张。**这意味着本版的上限更高，但下限更低（因为它更依赖数据）。**

**方差来源**：如果 H3 成立（质的问题），这是 strong accept 级的理论贡献；如果 H3 不成立，这只是一篇量化了"更快更难管"的工具论文。

## 10. 实测：Flask 基线标定（2026-09-15）

我在 §9 第 1 项里预测"用现有 Flask 历史估算 \(\lambda\) 与 \(R\)，看是否存在结构性跃升"可以产出一张论文级图表。**我做了，我的预测被否证了。** 如实报告结果，因为它比预测更有用。

**方法与可复现资产**：`03_基准与标注/benchmark/real-history/flask/git-history/estimate_lambda_R.py`（只读，不写入任何冻结资产；输出 `lambda_R_baseline.json`）。

### 12.1 实测值

| 量 | 值 |
|---|---|
| 提交总数 / merge 总数 | 5557 / 1027 |
| 历史跨度 | 2010-04-06 → 2026-09-08 |
| \(\lambda_{\text{merged}}\)（合入速率） | **0.172 merges/day** |
| tip-age 中位数（分支末端 → 合入） | **0.222 h**（约 13 分钟） |
| tip-age < 1h 的比例 | **64.5 %** |
| \(W\) 下界（中位数） | 0.222 h |
| **Little 积压下界** \(\approx\lambda W\) | **0.0016 changes** |

**按年中位 tip-age**（小时）：2012 **34.3** → 2013 **54.1** → 2017 0.32 → 2019 0.19 → 2020 0.06 → 2024 0.10 → 2026 0.06。

### 12.2 三条与预期相反的结果

1. **λ 没有跃升，而是在下降。** Flask 是收敛中的成熟项目（2010 年 555 commits/年 → 2026 年 81）。
2. **\(R\) 的时延不是恶化，而是塌缩了约 300–500 倍**（2012–2013 的数十小时 → 2020 年代的不到 10 分钟）。
3. **积压下界≈0。** 即：**在 Flask 上完全观察不到 \(\lambda>R\) 的失效态。**

### 12.3 这不是模型失败，而是模型的一次成功预测 + 一个测量学发现

**成功的一面**：Flask 是**前 AI 时代的健康基线**，而理论预测健康态就是"\(\lambda\approx R\)、积压有界且接近零"。实测正是如此。**这构成命题 1 的基线标定**——我们能识别"健康"长什么样，才可能识别"失配"。

**测量学发现（本文最有价值的一步）**：

> **失效态在原理上不可由 Git 历史观测。** 未调和的变更按定义就不在 commit 图里——工作区里未提交的混乱、被放弃的分支、从未合入的重复实现，全部落在 \(\lambda_{\text{merged}}\) 之外。因此

\[
  \lambda_{\text{produced}}-\lambda_{\text{merged}} = \text{积压}
\]

而现有的所有版本控制数据（包括本仓库全部基准资产）都只能看到左边第二项。

**这一条解释了两件事**：
1. **为什么这个领域缺数据**——不是没人重视，而是**主流数据源在构造上就看不到该现象**；
2. **为什么必须做 agent 侧插桩**——\(\lambda>R\) 的检验只能在能观测**产出速率**的通道上做，即 agent 与工作区侧，而不是仓库历史侧。

这也把本仓库此前那个更早的发现连成一条线：分支爆炸的样本（未合并的分支）在 merge 历史里同样被系统性排除。**两次都是同一件事：只看仓库历史，会系统性地看不到"没走完流程的变更"。**

### 12.4 对方案的影响（不粉饰）

- **§9 第 1 项作为"能立刻出图"的期望落空**：不能从成熟项目历史外推 agent 时代的 \(\lambda\) 跃升；
- **R2（"没有数据"）的分量反而上升**：本结果证明**必须**新建 agent 侧观测通道，这比"再找一批仓库"更重；
- **R3（"\(\lambda\) 与 \(R\) 不可测"）得到了一个具体的、可写进论文的答案**：可测，但**必须换观测通道**，且我们已给出规程与下界;
- **论文的主张必须相应收缩**：不能声称"我们观测到了 \(\lambda>R\)"，只能声称"我们给出了失配模型、健康基线标定、以及为何失效态不可由仓库历史观测的论证"。

### 12.5 \(\lambda\) 与 \(R\) 的估算规程（可写入论文，部分待实测）

| 量 | 估算方式 | 已知弱点 |
|---|---|---|
| \(\lambda_{\text{produced}}\) | **必须来自 agent/工作区侧插桩**：单位时间内产生的变更数（按任务边界归并） | 本仓库**尚无**此通道 |
| \(\lambda_{\text{merged}}\) | `git log` 合入速率（本脚本已实现） | 只是产出速率的**下界** |
| \(W\) 下界 | merge 时间 − 分支末端提交时间（本脚本已实现） | 不含写代码时间 |
| \(W\) 真值 | 需求认领 → 合入（需任务侧时间戳） | 需插桩 |
| \(R\) | 由 \(B(t)=0\) 的稳态反推：\(R\approx\lambda\)；失配期用 \(B(t)\) 的斜率估计 | 需 \(B(t)\) 可观测 |
| 积压 \(B(t)\) | **未调和变更数**：工作区未提交变更 + 未合入分支 + 未验证变更 | 需插桩；**这是核心仪表** |

**这张表就是 R3 的答卷**：每个量都给了估算方式与已知弱点，并诚实标出哪些尚无通道。审稿人可以质疑精度，但无法说"不可证伪"。

## 11. 诚实的边界

1. 场景为**多开发者 × 多 agent**；若数据只支持代理（人类并行 PR），全部结论必须限定为"并行变更流"层级——**这是本方案最脆的一环**；
2. **不主张** Git 在存储、分支或合并算法上有缺陷；只主张其**量级前提**（\(\lambda\approx R\)）被打破；
3. "代行 Git 功能"精确指代行其工作流中**人类调和职责**，不含对象存储与三方合并；
4. 若 K3 触发（agent 变更只是量的问题），本方案的理论贡献须主动降级，不得以"AI 原生"字样掩盖；
5. 若 K4 触发（收益来自阻塞），不得称为 AI 治理。
