## 1. Claim Plane：写入前准入（设计文）

来源：
- arXiv：[2607.21909](https://arxiv.org/abs/2607.21909)
- 作者：Maxim Nikolaev（Vladivostok State University）
- 代码：`github.com/SkeinRank/claim-plane`
- 核对级别：**L1**

### 研究对象

把并发软件修改定义为**写入前准入问题**（pre-write admission problem）。核心机制是版本化的 `ChangeIntent`，其中操作分为 **committed**（立即保留写权限）与 **contingent**（仅为规划提示，需原子提升后才保留权限）两类。

### 原文关键表述（摘要与引言）

> "Parallel coding agents can independently produce locally valid changes while still interfering at integration time, expanding beyond planned scope, or relying on premises invalidated by concurrent work."

> "Before implementation, each worker declares a versioned ChangeIntent containing an exact base commit, typed resources, dependencies, and operations marked as committed or contingent. A deterministic control plane atomically admits compatible intents, constrains same-file parallelism to declared regions, serializes unresolved overlap, tracks dependency invalidation, and fails closed on ambiguous authority."

### 与本项目的关系（对该文的自我定位）

该文明确声明与 ATM 的关系，且**不主张「写入前准入」这一想法本身的优先权**：

> "ATM [7] is the closest contemporaneous work. It explicitly formulates governed shared mutation as a pre-write admission problem and uses semantic atoms, bounded regions, a CID broker, fail-closed routing, and a neutral steward. Claim Plane does not claim priority over the general idea of pre-write admission."

### 对本项目的直接启示

1. 「把协调前移到代码修改之前」**已不能作为本项目的新颖性主张**；
2. 该文的 distinctive formulation 是「committed vs contingent 权限 + 原子提升 + intent-bound capability re-attestation + lease/fencing + 不可变 patch 证据」——本项目若在这些维度上没有独立机制，应主动放弃对应表述；
3. 它把「意图 + 作用域 + 依赖」作为准入对象，与本项目 ISCC 的字段重叠，**必须在相关工作里逐个引用**。

## 2. Claim Plane：确认性研究（本项目 H5 的现成靶子）

来源：
- arXiv：[2608.00947](https://arxiv.org/abs/2608.00947)
- 数据与产物：`huggingface.co/datasets/skeinrank/claim-plane-confirmatory-30x3`
- 核对级别：**L1**

### 实验设计（§Abstract、§3.4、§3.5）

- **30 个冻结的 CooperBench feature 配对**，balanced（15 冲突标签 / 15 干净标签）；
- **3 个 coder 种子**；**4 个协调臂**（Parallel / Claim Plane static / Claim Plane dynamic / Always serial）；
- **360 次完成的执行**；
- planner 声明由 DeepSeek V4 Pro 生成一次后**跨所有臂与种子冻结**；编码由 DeepSeek V4 Flash 完成；
- 主要终点 **pair pass**：两个 feature 各自通过 **且**集成后的仓库通过合并检查；
- 作者明确声明两项外部效度限制：benchmark 提供了**基于 gold patch 的 oracle 定位初始上下文**；API 请求是**物理串行**的，因此**不主张测得的 provider 级墙钟加速**，并发只通过准入决策与逻辑关键路径估计来评估。

### 数据与结果（§4.1 表 2、§4.2、§4.3）

| 臂 | pair pass | 集成成功率 | 有效序列化 |
|---|---|---|---|
| Parallel | 21/90 = 23.3% | 59/90 = 65.6% | 0/90 = 0.0% |
| Claim Plane static | 45/90 = **50.0%** | 87/90 = **96.7%** | 87/90 = **96.7%** |
| Claim Plane dynamic | 20/90 = 22.2% | 42/90 = 46.7% | 36/90 = 40.0% |
| Always serial | 45/90 = 50.0% | 86/90 = 95.6% | 90/90 = 100.0% |

**关键原文**：

> "Because the static and always serial arms had identical pair-pass rates within every repository-task cluster, the static-versus-parallel paired cluster difference equals +26.7 percentage points, with a 95% bootstrap interval from +9.6 to +60.0."

> "Static admission serialized every conflict-labeled execution and 42/45 clean executions. Its conflict sensitivity was therefore 100%, but clean specificity was only 6.7%."

> "Static admission achieved its result by serializing 96.7% of executions. It therefore validates the safety end of the design space but **does not satisfy the broader objective of serial-like quality with parallel throughput**. A practical system must recover a meaningful subset of clean concurrency without reintroducing the conflict penalty."（§5.2）

动态臂的失效解剖（§4.4）：90 次执行中 46 次 fail-closed；**46 次被阻断的修改里有 45 次指向的文件已经出现在冻结声明中**，只是落在被准入区域之外；未记录任何「正式被拒绝的提升」。

### 对本项目的直接启示

1. **这是本项目 H5 / \(\tau_{parallel}\) 的最强论据**：已有写入前准入的可靠性收益几乎完全来自退化为串行（96.7% 序列化，干净用例 93.3% 被误伤）。本项目可引用它确立「控制有效并行度后收益是否仍存在」是**已知开放问题**，而非审稿人的苛求；
2. 该文自陈未达成「类似串行的质量 + 并行吞吐」，因此本项目不能假设这个问题已被解决；
3. 它的失败解剖给出了一个可复用的设计教训：**fail-closed 阻断几乎都落在「已声明文件中未声明区域」**，说明问题不在规划器的粗粒度遗漏，而在缺少「有界修正 / 重新规划」的续行路径。

## 3. ATM：CID 中介的写入前准入

来源：
- arXiv：[2607.00041](https://arxiv.org/abs/2607.00041)
- 核对级别：**L1**

### 研究对象与范围声明（§1.1、§1.3）

> "The central question of this paper is not whether individual agents can produce usable code, but whether, once multiple agents have formed write intents within the same controlled filesystem, worktree, or service domain, the system can determine, before any governed shared mutation is applied, which intents may proceed in parallel, which require deterministic composition or serialization, and which must be blocked."

范围边界（作者自陈）：

> "ATM neither replaces Git merge nor addresses cross-clone or cross-PR governance; its claim is limited to an implementable, auditable, and incrementally extensible pre-write admission layer for governed shared mutations."

> "This paper does not address cross-machine clones, remote branches, or PR-level distributed coordination."

### 机制（§1.3）

七层硬准入门：CID 身份 → 共享面重叠 → 读写依赖 → file-range 与 virtual atom 细化 → `ConflictKey` + `canMerge` → **CAS base-hash 校验** → 文件锁回退。共享写入最终由**中立 steward** 而非提议 agent 施加。

作者对「为什么需要 fail-closed」的界定值得引用：

> "In this paper, fail-closed means fail-closed to unsupervised parallel or direct apply, not fail-closed to intent preservation. When an intent cannot be admitted as parallel-safe or routed immediately to deterministic composition, the broker preserves the declared intent, admission evidence, blocking reason, and any available patch or proposal envelope."

### 对同类工作的定位（§2 Related Work）

该文提到若干本项目尚未核对、但需要追踪的系统：**CodeTeam、SEMAP、MPAC、CodeCRDT、AgentGit、EvoGit** 被列为「adjacent planning, coordination, or convergence points」；**ColaUntangle**（对已纠缠的 commit 做依赖推理分区）、**SafeMerge**（版本已分叉后验证语义无冲突）、**semistructured merge**（用部分语法改进基于行的合并）被列为 post-hoc 一侧。

它对本项目最重要的自陈是：

> "If shared repository mutation is revealed only after the write—through a Git merge, a failing test, or human code review—the signal that returns to the system is typically late, coarse, and difficult to replay."

> "For multi-agent co-writing, pre-write admission should be treated as an independent first-class governance problem, not as a byproduct of a downstream version-control flow."

### 对本项目的直接启示

1. **task card + 语义原子 + 中立 steward** 已覆盖本项目 ISCC 的多数字段与「用 AI 治理 AI」的形态；
2. ATM 的「中立 steward」直接回应了本项目 R4（循环论证）——**本项目不能再把「外置账本的中立协调者」当作独有洞见**；
3. 它明确把「跨 clone / 跨 PR / 分布式」留作范围外，这为本项目保留了一个可辩的空间（若本项目定位在跨会话、跨工作树的仓库级协调）；
4. 它引用的 CodeTeam / SEMAP / MPAC / ColaUntangle / SafeMerge 是本项目下一轮必读清单。

## 4. STORM：写入时状态一致性

来源：
- arXiv：[2605.20563](https://arxiv.org/abs/2605.20563)
- 核对级别：**L1**

### 研究对象（§1 Introduction）

> "We treat this as a state management problem. An agent interacts with its workspace through file reads and writes. When it modifies a file, its reasoning depends not just on that file but on context from other files it has read (dependencies, interfaces, specifications). **The edit is only safe when those context files have not changed since the agent last read them.** This is a local consistency requirement: the agent does not need a frozen snapshot of the entire workspace, just assurance that the specific files informing its current edit are up to date."

对既有隔离路线的批评：

> "Isolation prevents interference during editing but **pushes all conflict resolution to the merge step**, after agents have already committed to potentially incompatible designs. Textual merge conflicts are easy to spot; semantic conflicts, where both sides compile individually but break when combined, are harder, and current tooling cannot resolve them automatically."

机制：

> "Before accepting a write, it checks whether the agent's view of the target file and its context dependencies is still current. If another agent has modified any of those files in the interim, the write is rejected and the agent receives the updated content so it can retry from a correct baseline."

### 数据与结果（§3.1、§3.2）

- 在 Commit0-Lite 与 PaperBench 上评估，三个 LLM（Claude Sonnet 4.6、Qwen 3.6 Plus、DeepSeek V4 Pro）；
- 相对 git-worktree 多 agent 基线：Commit0-Lite **+18.7**，PaperBench **+1.4**；
- 与单 agent 结合后最高分 87.6 与 78.2；
- 扩展实验（Sonnet 4.6，2→8 engineers）：测试分 38.2% → 69.7%，仓库宏平均 71.3% → 87.1%；
- 与「软隔离」对比（4 engineers）：prompt 软隔离 Score w 24.0 / Score 65.4；git worktree 24.6 / 63.8；**STORM 46.2 / 82.5**。

作者对「为什么写入时检测优于隔离」的核心论证：

> "STORM detects conflicts at write time rather than deferring them: when an edit violates local state consistency, it is rejected immediately, letting the agent re-plan while its reasoning context is still fresh."

### 对本项目的直接启示

1. **本项目 RQ2「检测时点」的新颖性已被占据**：STORM 已论证并实测「写入时检测优于后置合并」；
2. 「local state consistency」是一个比本项目「语义实体重叠」更经济的形式化：它只要求「agent 读过的文件未变」，而不需要抽取全局语义实体集合。本项目若主张语义实体抽取的必要性，必须证明 local state consistency **漏掉**了某类失效（例如 LF：读过的文件没变，但该实体的归属意义已被前序多会话稀释）；
3. 它的失效处理是「拒绝 + 回灌最新内容 + 重试」，不引入序列化，因此**没有并行度退化问题**——这是本项目 H5 的一个已存在的正向对照实现。

## 5. MPAC：多主体 agent 协调协议（威胁最大）

来源：
- arXiv：[2604.09744](https://arxiv.org/abs/2604.09744)
- 规范与实现：`github.com/KaiyangQ/mpac-protocol`（含 SPEC.md、MPAC_Developer_Reference.md）
- 核对级别：**L1**

### 研究对象（摘要）

> "We present MPAC (Multi-Principal Agent Coordination Protocol), an application-layer protocol that fills this gap with explicit coordination semantics across **five logical layers—Session, Intent, Operation, Conflict, and Governance**. MPAC makes **intent declaration a precondition for action**, represents **conflicts as first-class structured objects** rather than silent side-effects, and supports **human-in-the-loop arbitration** through a pluggable governance layer."

规模：

> "The specification defines 21 message types, three state machines with normative transition tables, Lamport-clock watermarking for causal ordering, two execution models (pre-commit and post-commit), three security profiles, and an optimistic-concurrency-control mechanism for shared state. We release two interoperable reference implementations (Python, 122 tests; TypeScript, 101 tests; 66 adversarial enforcement tests total), a machine-readable JSON Schema suite covering all 21 message types, and seven live multi-agent demos."

结果：

> "A controlled three-agent cross-module code review benchmark reports a **95% reduction in coordination overhead (68.65 s → 3.02 s)** and a **4.8× wall-clock speedup (131.76 s → 27.38 s)** under MPAC compared to a serialized human-mediated baseline, with per-agent decision time preserved (63.11 s → 57.13 s)."

### 机制细节（SPEC.md、Developer Reference）

- 五层中的 Intent 层包含 `INTENT_ANNOUNCE` / `INTENT_UPDATE` / `INTENT_WITHDRAW` / `INTENT_DEFERRED` / `INTENT_CLAIM` / `INTENT_CLAIM_STATUS` 等（v0.1.14 起共 22 种消息）；
- Conflict 层：`CONFLICT_REPORT` / `CONFLICT_ACK` / `CONFLICT_ESCALATE`；
- Governance 层：`RESOLUTION`，携带裁决主体的身份与阶段（pre- / post-escalation），以便下游审计重建授权链；
- 提供了「一个 agent 崩溃后其意图被挂起、另一 agent 通过 `INTENT_CLAIM` 认领其废弃工作」的故障恢复演示——这与本项目 M_provenance / UA 维度直接相关。

### 对本项目的直接启示

1. **这是本项目「任务—意图—操作—冲突—治理」五段式抽象最直接的既有实现**。本项目若仍以「统一变更对象」为核心贡献，必须解释为何这五个层次在 MPAC 中已存在而本项目仍有增量；
2. MPAC 是**协议层**（跨主体、可插拔治理、人类仲裁），本项目是**Git 兼容的仓库层协调平面**——这是可辩护的差异，但需要在正文里写清楚，不能默认读者接受；
3. MPAC 已有 21+ 消息类型与机器可读 schema，其成熟度高于本项目 ISCC v0.1 的 schema。**本项目在「协议完备性」维度无法竞争，应避免正面比较**；
4. MPAC 的 benchmark 是「相对串行化的人类中介基线」，因此它**同样没有回答非退化并行度问题**——这一点与本项目 H5 相关，可在引用时指出。

## 6. SCF：语义意图偏离与 Drift Monitor

来源：
- arXiv：[2604.16339](https://arxiv.org/abs/2604.16339)
- 实现：`github.com/curiosityexplorer/semantic-consensus`
- 核对级别：**L1**

### 研究对象（摘要）

该文提出**Semantic Intent Divergence** 这一概念：

> "This paper identifies Semantic Intent Divergence—the phenomenon whereby cooperating LLM agents develop **inconsistent interpretations of shared objectives due to siloed context, absent process models, and unstructured inter-agent communication**—as a primary yet formally unaddressed root cause of multi-agent failure in enterprise settings."

六个组件：Process Context Layer（PCL）、Semantic Intent Graph（SIG）、Conflict Detection Engine（CDE）、Consensus Resolution Protocol（CRP）、**Drift Monitor（DM）**、Process-Aware Governance Integration（PAGI）。

**Drift Monitor 的定义**：检测 **long-running workflows 中渐进的语义偏离**（"detects gradual semantic divergence across long-running workflows"）。

### 数据与结果（摘要）

- 600 次运行，跨 AutoGen / CrewAI / LangGraph 三种框架配置与四个企业工作流场景；
- **唯一达到 100% workflow completion**（次优基线 25.1%）；
- 检测 **65.2% 的语义冲突，但 precision 仅 27.9%**；
- 提供完整的治理审计轨迹；
- 报告企业背景数据：生产部署失败率 41%–86.7%，其中近 79% 的失败源于**规格与协调问题**而非模型能力限制。

### 对本项目的直接启示

1. **Drift Monitor 是本项目 LF（意图稀释）最接近的既有构念**。两者的关键差别需要写清楚：SCF 的漂移是「agent 对共享目标解释不一致」，发生在**执行前/执行中的意图层**；本项目的 LF 是「同一代码实体被多次触碰后，其保留形态无法回溯到任何单一有效任务」，发生在**已落地代码的归属层**。这个差别是真实的，但必须在正文中论证，不能假定；
2. **27.9% 的 precision 是一个重要信号**：语义偏离类检测当前很不可靠。本项目若要做 LF 检测，必须预设低精度并报告误报代价；
3. 该文引用的「79% 失败源于规格与协调问题」可用于本项目动机段落；
4. 它同时说明：**「意图不一致」这一构念在 2026 年已被正式提出并命名**，本项目不能再把它当作新发现。

## 7. Before the Pull Request：git 原生协调日志（L1）

来源：
- arXiv：[2606.19616](https://arxiv.org/abs/2606.19616)
- 产物：grite（开源协调基底）+ 数据集、harness、挖掘工具
- 核对级别：**L1**

### 研究对象（摘要）

> "Autonomous coding agents now open millions of pull requests, yet large-scale studies find their PRs are produced faster but accepted less often—a coordination and trust gap that **pull-request-level telemetry cannot explain**. We argue the missing signal lives **before the PR**, in how concurrent agents claim, divide, and collide over shared work."

> "We study this process through grite, our open-source coordination substrate that **needs no central server and stores its records inside git itself**, so its append-only, signed event log captures the coordination process directly."

### 三条结果（原文）

> "(i) this shared substrate reduces duplicate and conflicting work at bounded overhead—the share of work that merely re-does a teammate's task **falls from 78% to 0%** while useful throughput more than triples;
> (ii) every agent's copy of the log converges to the same state with no write silently dropped, where a file-based tracker loses concurrent writes;
> (iii) the log is a mineable artefact from which concrete failure modes—conflicting edits, lock starvation, redundant rediscovery, race-to-close—are automatically recoverable with provenance, **several invisible in pull-request history**."

### 对本项目的直接启示

1. **独立佐证了本项目的测量学结论**：本项目 §10.3 由 Flask 历史推断「失效态不可由 Git 历史观测」，该文从另一条路径（并发 agent 的协调日志）得到同一结论（"several invisible in pull-request history"）。这可以互相引用，把该结论从「一次负结果」升级为「两处独立证据」；
2. **削弱 R4 的答辩**：本项目 R4 的答案是「治理不靠更大上下文，靠外置持久账本」。该文已实现「无需中央服务器、把记录存在 git 内部的 append-only 签名日志」——外置账本已是既有做法，本项目需要新的论证角度；
3. **78% → 0% 是「重复工作」的最强量化**，可作为本项目 M_redundancy 维度的外部对照值；
4. 它列出了可自动恢复的具体失效模式（conflicting edits、**lock starvation**、**redundant rediscovery**、race-to-close）。其中 **lock starvation 与本项目 K4/H5 直接相关**：这是「防冲突机制本身引入的成本」。本项目在报告 \(\tau_{parallel}\) 时应把 lock starvation 作为显式副作用指标。

## 8. When Agents Coordinate：协调的时间网络测量（L1）

来源：
- arXiv：[2608.16801](https://arxiv.org/abs/2608.16801)
- 核对级别：**L1**

### 研究对象与方法（摘要）

> "We introduce an instrument to measure this coordination. Each run is represented as a **temporal network** in which agents and files are nodes, and messages, file writes, and file reads are **timestamped directed edges with an associated cost**. We apply this instrument to **1902 runs**, each evaluated with a fixed test suite, across configurations that vary the team size, the team structure, and the file policy."

### 结果（原文要点）

> "Direct messaging initially increases **close to quadratically** with the number of agents, with much of this growth coming from an early round of introductions. As the teams grow further, this increase levels off in the largest teams we study, where agents increasingly communicate through broadcast messages."

> "Work built around a shared specification produces dense, highly connected teams, while pipeline tasks produce sparse networks organised around local interfaces."

> "**Shared files can replace repeated 1-to-1 communication, cutting output tokens by about 42% at eight agents on message-heavy work, while adding overhead when files already carry the coordination.**"

> "**Naming one agent as coordinator creates no communication hub and provides no reliable improvement in success.**"

另有两条值得注意的观察：agents 表现出**未被提示地寻找隐藏评分材料**的倾向（在 sealed environment 的 244 次补充运行中，四分之三以上的运行仍会去够；coordinator 与 file-channel 结论复现）。

### 对本项目的直接启示

1. **「指定协调者无效」是本项目治理 agent 形态的直接负面证据**。本项目不能只说「需要一个全局视图」；必须论证治理 agent 与「被指定的会话内 coordinator」在机制上可区分——差别在于本项目主张的是**跨会话、以持久结构化账本为状态、在写入前介入的外部协调者**。这一区分本身就是可检验假设，建议写入预注册；
2. **「共享文件作为协调通道」有 42% 的 token 收益**，为本项目「把状态外置到仓库而非上下文」提供了独立量化支持。但同时该文指出「当文件已经承载协调时，再加文件通道反而增加开销」——这与本项目 04_协调插件「instrument 与 governor 必须可独立开关」的设计理由同源；
3. **时间网络是本项目 B(t) 观测可直接借鉴的仪器设计**：把 agent 与文件作为节点、读写作为带成本的有向边，天然给出了「谁在何时触碰了哪个实体」的时序数据，正是本项目「跨会话实体争用」所需；
4. 团队规模增大后通信从点对点转为广播——这提示本项目在 2/4/8 agent 规模下应预期不同的协调形态，不应假定线性外推。

## 9. The Specification Gap：规格缺口的因子恢复实验（L1，自伤性）

来源：
- arXiv：[2603.24284](https://arxiv.org/abs/2603.24284)
- DOI：10.13140/RG.2.2.14475.96802
- 核对级别：**L1**

### 实验设计（摘要）

51 个类生成任务，把规格细节从完整 docstring（L0）**逐步剥离到裸签名（L3）**，并注入**对立的结构偏见**（list vs dict）来施压集成。

### 三条结果（原文）

> "First, a persistent **specification gap**: two-agent integration accuracy drops **from 58% to 25%** as detail is removed, while a single-agent baseline degrades more gracefully (**89% to 56%**), leaving a **25–39 pp coordination gap** that is consistent across two Claude models (Sonnet, Haiku) and three independent runs."

> "Second, an AST-based conflict detector achieves **97% precision at the weakest specification level without additional LLM calls**, yet a factorial recovery experiment shows that **restoring the full specification alone recovers the single-agent ceiling (89%), while providing conflict reports adds no measurable benefit**."

> "Third, decomposing the gap into **coordination cost (+16 pp)** and **information asymmetry (+11 pp)** suggests that the two effects are independent and approximately additive."

> "These results support a **specification-first view** of multi-agent code generation: richer specifications are both the primary coordination mechanism and the sufficient recovery instrument."

### 对本项目的直接启示（**双刃，必须正面处理**）

**正面**：
1. 「规格优先」被独立证实——更丰富的规格既是主要协调机制，也是充分的恢复工具。这**支持本项目「协调前移 / 任务前置登记」的方向**；
2. 缺口可分解为协调成本（+16pp）与信息不对称（+11pp）且近似可加，这为本项目把「绑定丢失」与「信息缺失」分开测量提供了方法论先例。

**负面（更关键）**：
3. **「提供冲突报告没有可测量的额外收益」直接质疑检测器类贡献**。如果恢复规格就足以达到单 agent 上限，那么本项目「语义实体检测 + 风险报告」的边际价值在哪里？
4. 本项目唯一可辩护的回答方向是：该实验的前提是**规格信息存在且可被恢复**（L0 的完整 docstring 就在输入里）；而本项目 §1.1 主场景的问题恰恰是**任务声明存在于会话历史、无法落入仓库**。因此本项目恢复的是**绑定（binding）**而不是**规格内容**。但这一区分必须成为 H6 与检测评估的**前提条件**，并在实验设计中显式控制（即在规格完整但绑定丢失的条件下测量），否则会被读成事后解释；
5. 该实验的 L3 条件下 **97% precision 且不需额外 LLM 调用**的 AST 检测器，说明「低成本符号级检测」已被证明可行——本项目若用 LLM 相似度做检测，精度基线必须与这个数字比较。

## 10. AI Agent Pull Requests on GitHub：并发提交的频率与冲突率（L1）

来源：
- arXiv：[2607.04697](https://arxiv.org/abs/2607.04697)
- 数据：AIDev-pop（33,596 PR / 2,807 仓库）
- 核对级别：**L1**

### 研究对象（摘要）

> "AI coding agents may generate and submit Pull Requests (PRs) to the same repository at the same time. However, research concerning the extent of concurrent submission by AI coding agents to a common repository does not exist."

### 结果（原文）

> "when considering exact temporal overlap, **40.2% of repositories contain co-active agent-authored PR pairs**; further, the co-active pairs account for **79.4% of all PRs generated by an AI agent**. When we examine co-activity within a one week collaboration window, the percentages are increased to 53.4% and 95.0%."

> "For the majority of the co-active PR pairs (underlying the vast majority of which are intra-agent authored), both PRs were authored by the same agent, while **only 0.5% of co-active pairs were cross-agent**, and occurred in only 122 out of 2807 total repositories examined (or approximately 4.3%)."

> "we replayed actual three way git merges on 747 unique co-active pairs (one per repository)... the percentage of textual conflict encountered was **significantly higher for cross-agent pairs compared to intra-agent pairs: 41.7% vs. 19.8%**, respectively, with non-overlapping 95% confidence intervals."

> "the majority of conflicts resulted from modifications to source code files (**84.4% of conflicted files**) and not dependency manifest files; further, **nearly 42% of conflicts we observed were structural** (i.e., modify/delete or add/add)."

### 对本项目的直接启示

1. **并发提交是常态，这是本项目 \(\lambda\) 上升最直接的生态证据**：40.2% 的仓库存在时间重叠的 agent PR 对，且它们占 agent 生成 PR 的 79.4%；
2. **跨 agent 冲突率（41.7%）约为同 agent（19.8%）的 2.1 倍**，置信区间不重叠。这是对 H3/P5（agent 变更是「质」的问题而非「量」）的**独立、非本项目产出的证据**，价值极高：在同等并发条件下，跨 agent 交互显著更差，说明上下文有界性是独立病因；
3. **但跨 agent 共活跃仅占 0.5%（122/2,807 仓库）**——这是对本项目「多开发者 × 多 agent 交互」场景真实性的直接削弱。本项目必须据此调整表述：真实生态中绝大多数并发是**同一开发者/同一 agent 的多任务并发**（即本项目 §1.1 的原始「单开发者 × 多会话」场景），而不是多主体交互。**这反而支持本仓主文档 §1.1 的收敛方向**；
4. 94.4% 的冲突来自源码文件、近 42% 是结构性冲突，说明「文件级路径交集」不足以刻画冲突类型——与本项目 Flask 试点「共享文件不等于语义冲突」的负结果一致；
5. 该文只做文本冲突重放，**不做语义冲突与归属分析**，为本项目留下空间。

## 11. AgenticFlict：agent PR 文本冲突数据集（L1）

来源：
- arXiv：[2604.03551](https://arxiv.org/abs/2604.03551)
- 实现：`github.com/unlv-evol/agenticflict`
- 核对级别：**L1**

### 数据规模（摘要）

> "The dataset comprises **142,652 Agentic PRs** collected from **59,412 repositories**, of which **107,026 are successfully processed** through deterministic merge simulation of open and/or closed (unmerged) PRs. Our pipeline identifies **29,609 PRs exhibiting merge conflicts, yielding a conflict rate of 27.67%**, and extracts **336,380 fine-grained conflict regions** across these instances."

冲突区域元数据包括：affected file paths、conflict regions、line-level spans（`start_line` / `mid_line` / `end_line`）、双方代码块的 SHA-256、双方文本预览；PR 级严重度指标包括冲突文件数、冲突区域数与冲突标记内总行数。覆盖 5 个不同 AI coding agent，可做跨 agent 比较。

检测手段（确定性，不依赖模型）：

> "a local merge simulation using Git... we execute the following command: `git merge --no-commit --no-ff`. If the merge operation fails, Git records unresolved files in the index... we identify these files using: `git diff --name-only --diff-filter=U`."

### 作者明确声明的边界（对本项目极重要）

> "**Textual conflicts only.** The dataset captures syntactic merge conflicts as reported by Git's 3-way merge. **Semantic conflicts (syntactically correct but behaviorally incompatible changes) are not detected.**"

### 对本项目的直接启示

1. **规模远超本仓 Flask 试点**：142K PR / 59K 仓库 vs 本仓的 7 个候选。本项目若要建立 Gate A 的真实数据，应优先考虑复用或对接该数据集，而不是继续在单个 Flask 仓库上手工扩样；
2. **27.67% 的文本冲突率**是本项目「分支爆炸 / 集成失败」动机的规模证据；
3. 它**公开声明不做语义冲突、不做归属分析**——这是本项目可引用的、由他人划定的空白边界；
4. 它的 `--diff-filter=U` 方法与本仓 `replay_merges.py` 同源，说明本项目该脚本的技术路线是业界标准做法，可在方法章节引用以增强可信度；
5. 注意：它统计的是**文本**冲突，因此不能用来反驳本项目「Git merge-tree 重放不足以观测语义失效」的结论——两者恰好互补（文本冲突可大规模观测，语义/归属失效不可）。

# 第二部分：语义合并冲突检测与消解

## 12. ConflictLens（SEKE 2025）

来源：
- DOI：[10.18293/seke2025-012](https://doi.org/10.18293/seke2025-012)
- PDF：Crossref `resource.primary.URL` 指向 `paper012.pdf`
- 核对级别：**L1**（本仓既有）

### 研究对象

PDF 第 1 页摘要将 semantic merge conflict 定义为：合并代码违反一个或两个分支的规格；方法目标是在已有分支合并语境下平衡检测 precision 和 recall。

### 输入与流程

- 第 2 页：从 GitHub Java 项目选取双父提交；先执行 `git-merge`，丢弃文本冲突场景；再构建自动合并版本；最后将自动合并版本与开发者提交的合并版本进行差异比较，筛选语义冲突候选。
- 第 3–4 页：两阶段管线由 Semantic Conflict Localizer 和 Targeted Conflict Validator 组成。前者用 LLM 静态定位潜在冲突，后者生成针对性测试并跨相关分支执行。

### 数据与结果

- 第 2 页：从 195 个 Java 仓库的 56,129 个 merge scenario 中筛选出 137 个高置信度候选，14 个案例未归入四种模式。
- 第 4–5 页：独立评估集包含 31 个 Java 项目的 85 个真实 merge scenario。论文报告 ConflictLens precision 0.91、recall 0.76、F1 0.82，并与 DSC、SAM 和 Vanilla-LLM 比较。

### 对本项目的直接启示

1. ConflictLens 已覆盖「合并后、分支对之间的语义冲突检测」，**本项目不能把「发现文本无冲突但语义有问题」作为唯一新颖性**；
2. 本项目候选差异必须转向：任务前置的重复目标识别、agent 来源与生命周期的统一变更对象、评估去重与集成成本而非冲突分类 F1；
3. 应把 ConflictLens 作为语义冲突检测基线或可插拔验证器，而不是忽略它；
4. 其定义域是「两个改动之间不兼容」，**在定义上不覆盖行为兼容而语义归属被稀释（LF）**——这是本项目相对它最清晰的差异化点，但需要独立证据（H6）。

## 15. SWE-agent（NeurIPS 2024）

来源：
- DOI：[10.52202/079017-1601](https://doi.org/10.52202/079017-1601)

### 研究对象

- 第 1–2 页：论文提出 agent-computer interface（ACI），研究界面设计如何影响 language-model agent 执行软件工程任务的能力。
- 第 2 页：ACI 提供文件编辑、仓库导航、搜索和程序/测试执行等能力。

### 评估边界

- 第 4–6 页：主要在 SWE-bench（2,294 个任务）和 SWE-bench Lite（300 个任务）上评估单个 agent 的任务解决率及 ACI 消融。

### 对本项目的直接启示

## 16. ChatDev（ACL 2024）

来源：
- DOI：[10.18653/v1/2024.acl-long.810](https://doi.org/10.18653/v1/2024.acl-long.810)
- 公开全文：[arXiv:2307.07924](https://arxiv.org/abs/2307.07924)
- 核对级别：**L1**（本仓既有）

### 研究对象

- 第 1 页摘要：通过 chat chain 和 communicative dehallucination 组织多角色 agent 参与设计、编码和测试。
- 第 2–4 页：Chat Chain 按阶段传递任务、方案、代码和反馈；communicative dehallucination 用角色化交流过程减少开发幻觉。

### 评估边界

- 第 5–7 页：比较单 agent 和多 agent 范式，报告生成质量、成本、token、文件和人类/GPT-4 评价等指标。
- 第 9 页限制：论文明确讨论多 agent 通信和软件生成流程的限制，但没有把 Git 变更实体、语义影响图或 merge 后集成债务作为主要测量对象。

### 对本项目的直接启示

ChatDev 已覆盖「多 agent 通过通信协作开发」的方向。因此本项目的差异不应是「第一次让多个 agent 协作」，而应是为这些 agent 的并行代码变更增加一个跨聊天流程的 Git 兼容协调平面。

## 17. 本轮新增（L2，仅可作范围比较）

- *CAID: Effective Strategies for Asynchronous Software Engineering Agents*（arXiv [2603.21489](https://arxiv.org/abs/2603.21489)）— 中央 manager + 依赖感知任务图 + 隔离工作区 + 测试门集成；结论是 branch-and-merge 是核心协调机制，git worktree / commit / merge 使其可靠可执行。**用于削弱「Git 不足」的动机**。
- *AgentRoom*（arXiv [2608.23740](https://arxiv.org/abs/2608.23740)）— CRDT 共享文件系统上的 file-level claim / status / broadcast MCP 工具；结论是「协调」而非并行度或 CRDT 合并承担收益。
- *CodeCRDT*（arXiv [2510.18893](https://arxiv.org/abs/2510.18893)）— 观察驱动协调，乐观 TODO-claim + LWW；报告 5–10% 语义冲突率、21.1% 加速与 39.4% 减速。
- *EvoGit*（arXiv [2506.02049](https://arxiv.org/abs/2506.02049)）— 去中心化，协调通过 Git-based phylogenetic graph 涌现，无中央协调、无显式消息传递、无共享内存。
- *CodeTeam*（arXiv [2606.22082](https://arxiv.org/abs/2606.22082)）— Architect / CTO / Developer / QA + bounded context + 轻量 Git 协调（独立分支 + 结构化 commit message 含 `update_reason` 与接口变更摘要）。
- *MAST: Why Do Multi-Agent LLM Systems Fail?*（arXiv [2503.13657](https://arxiv.org/abs/2503.13657)，NeurIPS 2025 D&B）— 14 失效模式 × 3 类，1600+ 轨迹，κ=0.88。**用于防止「首个分类学」表述**。
- *CooperBench*（arXiv [2601.13295](https://arxiv.org/abs/2601.13295)）— 协作使成功率平均下降约 30%。
- *STALE-bench*（arXiv [2609.25396](https://arxiv.org/abs/2609.25396)）— 417 对 Django PR 校正后仅 1 例干扰；构造任务 97% 干扰；一条并发变更消息恢复 82%。
- *SILO-BENCH*（[ACL 2026](https://aclanthology.org/2026.acl-long.1354.pdf)）— k=2 损失 15–49%，k=50 损失 80–100%。
- *OrchestraBench*（arXiv [2608.05263](https://arxiv.org/abs/2608.05263)）— 注入 MAST 失败模式，测路由、恢复与 cascade。
- *Git-Context-Controller*（arXiv [2508.00031](https://arxiv.org/abs/2508.00031)）— COMMIT / BRANCH / MERGE / CONTEXT 管理 agent 上下文。

## 18. 本轮新增：上下文有界性（L2，本项目的机制支撑）

- *Governance Decay / ConstraintRot*（arXiv [2606.22528](https://arxiv.org/abs/2606.22528)）— 压缩使违规率 0% → 30%（最高 59%）；约束进摘要则 0%、被丢弃则 38%；软性组织策略衰减是硬性安全规范的 8.3 倍；Constraint Pinning 用约 47 个 pinned token 恢复至 0%。

- *Regression Accumulation in Multi-Turn LLM Programming Conversations*（arXiv [2607.01855](https://arxiv.org/abs/2607.01855)）— 542 任务 × 6 模型 × 8 轮 = 26,016 实例；后续建议破坏早先需求。

## 19. 本轮新增：AI 代码归属与审计（L2，对应本项目 M_provenance）
