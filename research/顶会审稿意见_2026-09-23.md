# 顶会审稿意见：AI 原生变更协调研究

评审日期：2026-09-23。评审口径：ICSE / FSE / ASE 主研究轨的完整研究论文；不代表任何会议的正式意见。

## 评审范围与结论

对工作区做了文件清单与研究关键词检索，评审主体定位为 `AI原生变更协调研究/`。重点核对问题定义与历次定位、相关工作矩阵与原文摘录、标注规范、现有结果、预注册，以及治理插件的策略、账本、宿主接线和测试。外部依赖、其他项目和制图产物不作为该研究的原创贡献；没有逐字阅读全部第三方源码/PDF，也没有进行新的系统性文献检索。因此本意见不声称已证明领域中不存在相同工作。

**建议：Reject（当前完整研究论文形态）。** 问题值得研究，原型和可复现基础已有实际投入；但主张、测量和实现没有形成闭环。阻碍不仅是缺数据，现有仪表的构念混淆和宿主数据链路缺口会使未来实验也难以解释。建议先修研究设计，再采正式数据。

对实现与当前证据缺口的判断置信度高；对相对整个领域的新颖性的判断置信度中等，取决于进一步文献审计。

## 你们写出的痛点

主要来源：`01_问题定义与定位/AI原生版本控制研究问题.md` §1–2，以及当前总纲 `痛点_速度与上下文失配.md` §2–6。

| 痛点 | 具体内容 | 审稿判断 |
|---|---|---|
| 任务与改动的绑定丢失 | 任务留在会话里，代码落在工作树里，会话结束后难以重建归属 | 最清晰、最容易形成可测研究问题 |
| 无冲突也不可理解 | 同一实体反复修改，行为兼容但难以解释最终状态为何如此 | 有价值，但 LF 定义需要排除正常的多任务共同演化 |
| 重复实现与概念分歧 | 不同会话重复完成同一目标，或建立不一致的命名、接口 | 合理，但需要超越文件重叠的语义真值 |
| 共享工作区污染 | 半成品、未提交修改无法关联到有效任务和状态 | 需要工作区/会话轨迹，人类已合并 PR 不能替代 |
| 隔离后的集成负担 | 分支增多、未合并或废弃变更累积 | 合理，但当前主线 merge 样本系统性缺少这些对象 |
| 速度与上下文失配 | 变更到达速率超过归属、验证与集成能力；有限上下文进一步破坏协调 | 可作为统一假设，尚不是已经证实的因果机制 |

更稳妥的痛点表述：

> 多会话 agent 并行开发时，任务意图、执行来源与实际代码修改分散在不同会话和工作区中，现有工作流未必能持续维护它们的可核查关系。这可能增加重复实现、归属重建与集成成本；本研究检验持久化任务—变更绑定及跨会话协调是否能改善这些结果。

不应把“每个 agent 局部正确”“AI 提高变更速率几个数量级”“Git 以 λ≈R 为设计前提”写成已确立事实。当前仓库没有对应证据。

## 主要拒稿理由

### R1. 核心机制尚未被识别，当前比较不能证明上下文是病因

当前总纲第 114、192 行把同等 λ/R 下 agent 更差解释为“上下文有界性被证明是独立病因”。这不成立：能力、任务难度、工具、测试覆盖和工程经验都可能造成差异。人类同样具有有界记忆。`compaction/end` 是压缩事件，不等于相关信息确实丢失；长任务本身既更容易压缩，也更容易失败。

预注册 E5 用 Flask 人类历史对比新采 agent 轨迹，还存在观测口径差异：历史没有同等的 produced stream、上下文状态和未完成工作量，不能直接匹配所需 λ/R。

建议在相同模型、仓库、任务和资源预算下，随机操纵上下文保留/压缩方式与跨会话信息共享，检验“被遗漏的信息—错误决策—结果损失”的链条。人类对比只能补充生态意义。

### R2. 积压模型有数学错误，Flask 结果被过度解释

总纲第 89 行使用 B(t)=∫max(0,λ−R)dt。该量只增不减，无法表示服务能力富余后排空积压。例如先每小时到达 2、服务 1，积压 1；下一小时到达 0、服务 1，实际积压归零，原公式仍为 1。

建议用事件守恒：B(t)=B(0)+A(t)−D(t)−X(t)，分别明确到达、完成调和及废弃/撤销；或采用有零边界的流体队列。若 R 是能力而非实际完成速率，需要另写服务约束。即使 λ(t)>R(t) 始终成立，也需累计正漂移发散等条件才能推出无界增长，不能只看严格不等号。

总纲 §12.3 的“λ_produced−λ_merged=积压”量纲错误：速率差至多对应积压变化率，且还需处理废弃与返工。`estimate_lambda_R.py:170` 用 tip-age 中位数乘总体合入速率，不能直接作为 Little 定律的平均 WIP 下界：Little 定律要求一致系统边界及相应均值/稳态条件，中位数不是均值。

“下界接近零”不能推出“真实积压接近零”或“健康基线得到验证”。80 次自动合并树一致也不能证明分支隔离失败、没有语义问题，或支持上下文机制。未合入分支也可能已经有 Git commit；正确限制是“仅观察已合入主线的历史不足以完整识别失配”。

### R3. 并行度指标与积压共用同一序列，核心 H5 不可由此验证

`src/ledger.ts:481` 的 `computeParallelism` 对 `backlogSeries` 积分；`buildReport` 将同一开放胶囊序列用于 B 和 P。于是这里的 P 实质是平均未调和工作量，不是实际同时执行的 agent 数。排队、闲置、卡住等待审批的任务也被当作并行工作。

这会产生相反解释：成功更快集成使开放任务减少，可能触发预注册的“并行度下降→只是限流”；反之保留大量闲置任务就能让 P 看起来很高。建议另行采集模型/工具执行区间、等待区间与真实完成吞吐，分开报告 WIP、执行并发和延迟。15%/25% 的阈值只能表达预设约束，不能证明收益的因果来源。

还复现了窗口不一致：两次任务开启位于第 0 和第 1 小时，最后一条普通事件在第 10 小时，速率窗口为 10 小时，而 P 窗口只有 1 小时，`parallelFraction=0`，遗漏后续尚未关闭的 9 小时。需统一显式观察终点。

### R4. 纯函数实现通过测试，真实宿主仍缺研究所需的信息闭环

在 `src/plugin.ts` 和 `src/governor.ts` 核对到：

1. `observeWriteIntent` 写入 `file_write` 时没有传 `intentText`；`noteGate` 也未保存 proposal 的意图。`buildCapsules` 只从 `file_write.intentText` 提取历史意图。因此当前宿主路径无法自然形成 E2 构造数据中完整的历史意图表。
2. 宿主接线没有发出 `lifecycle_integrated` 等完成调和事件，也没有明确任务登记接口；任务默认回退为 session ID。一次会话多个任务可能被压成一个胶囊，完成调和速率及积压则依赖外部补事件。现有接线本身不足以支撑该测量。
3. 各 `GovernorRuntime` 使用实例内存账本；磁盘仅 append，没有跨进程读取/订阅与恢复路径。同一实例的多会话可以共享，多个独立宿主进程尚不能由这套接线共享治理视图。复现中相同写入在原实例可被判为争用，在另一实例判 `no-contention`。多开发者、多窗口场景必须明确部署拓扑。
4. `aggregateEntities` 汇总所有历史胶囊，没有按是否仍在飞过滤；已完成任务可能继续被当作正在修改的竞争者。应区分持久来源检索与当前写入争用。

这些是正式实验前应解决的效度问题。现有单元测试不能替代真实多会话闭环。

### R5. E2 的 0.8 不是语义检测有效性的证据

`results/E2/eval.json`：8 个构造案例，TP=4、FP=1、FN=1、TN=2。Precision=4/5，Recall=4/5。两个语义重复案例以 `cross-task-conflict` 被检测，意图分数仅 0.286 和 0.083，低于 0.42。它们被文件/实体重叠兜底命中，不证明识别了语义重复。

`policy.ts` 先按相同 entityKey 筛选，再计算词法 Jaccard；不同文件的重复实现不可由当前匹配路径发现。A4 在 3 个独立对照中拒绝 1 个；A3 误拒为零来自“不执行拒绝”的配置，仍有 1/3 的对照误报警。

因此 E2 是开发阶段校准结果。需增加同文件不同目的、跨文件同意图、读写依赖、否定意图、非英语任务及上下文残缺场景；开发集与冻结测试集分离，比较文件重叠、词法匹配、共享任务表和语义方法。小样本点估计不能用作总体门槛已获统计保证的证明。

### R6. LF 定义可能把正常组合式演化判为失败

`GateA标注与基准规范.md` §4.9 以“保留形态无法回溯到任何单一有效任务”为条件。但一个函数同时服务于任务 A 与 B 很正常；不能用一个任务完整解释，并不代表无法由多个任务共同解释。

应测“在提供有效任务集合、约束和变更证据后，能否重建关键设计选择”，允许多对多绑定，并测重建正确率、耗时与维护错误。3+ 次触碰只能用于采样，不能直接作为失败证据。当前 7 个候选没有双人完整标注，合成集也没有 LF 正例，暂时不能声称已建立独立失效类别。

### R7. 新颖性对比不足，实验主要还是内部配置比较

目前的 6 篇文献矩阵及部分全文核对不足以覆盖 IDE 协作感知、任务上下文、需求可追踪性、变更影响分析、共享黑板/记忆、并发控制和增量验证等直接相邻方向。缺少覆盖不能被写成不存在先行工作。

A0–A4 有助于隔离插件组件，但没有回答“为什么不使用共享任务登记、Git worktree、实体锁/预约、已有追踪/协作机制”。需要预算匹配的强基线；不要求每条路线都比较所有工具，但必须覆盖与最终主张最接近的方法。

### R8. 预注册与复现状态不一致

`05_实验/preregistration.md` 开头仍写 DRAFT、未冻结且禁止冻结前 E2 采集，后文及 E2 报告却使用“冻结门槛”。本工作目录顶层也不是 Git 仓库，当前可见材料不能验证何时冻结以及相对于采集的时间先后。可将现有 E2 明确登记为开发性 pilot，并为后续测试集建立可核查的版本/时间戳；不应追溯性声称已预注册。

功效规则若要求 N>40，简单缩小任务包不保证解决功效不足；主指标是比例且可能为零，直接对数分析也需说明零值、分母和聚类处理。固定输出轨迹回放适合仪表校验，若模型不能响应干预则不能据此估计在线治理效应。

## 作者应优先完成的工作

1. 固定研究对象：先用单开发者、多会话完成端到端证明，再说明多开发者推广边界；或直接补足多进程共享、归属和同步机制。
2. 修正队列数学、λ/R 单位、任务边界和完成条件。把实际执行并发从积压中独立出来，并统一观测窗口。
3. 打通真实事件闭环：任务登记→携带意图的写入→验证→集成/废弃→跨会话可见→可重启恢复。用原始宿主日志独立核对。
4. 把现有 E0/E2 标为开发性校准，冻结新测试集与可核查协议；补双人盲评与失败运行。
5. 先证明一个窄收益：持久任务—变更绑定是否降低重复实现或归属重建成本。对比共享任务表/简单重叠提示等强基线，在统一资源预算下报告有效完成数、真实并发、延迟与成本。
6. 通过上下文保留×跨会话信息共享的控制实验检验机制，再决定是否保留“速度—上下文失配”的理论主张。

能够改变本评审结论的证据，是可信的真实多会话测量、修复后可审计的系统闭环，以及对强基线的稳定增益。增加定义、公式或单元测试数量本身不会消除这些主要疑虑。
